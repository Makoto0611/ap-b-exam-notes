## 1. オブジェクト指向（令6秋、令6春、令3春）

### 基本用語
| 用語 | 意味 |
|---|---|
| クラス | 属性（データ）とメソッド（操作）をまとめた、オブジェクトの設計図 |
| インスタンス | クラスから作った、実体 |
| カプセル化 | 内部のデータを隠し、メソッド経由でだけ扱わせる |
| 継承 | 既存のクラス（親）の性質を、子クラスが引き継ぐ |
| 抽象クラス | 一部のメソッドを、実装せず、子クラスに任せるクラス |
| インタフェース | メソッドの名前と型だけを決める。実装は持たない |
| 多相性（ポリモーフィズム） | 同じメソッド名の呼出しでも、実際のオブジェクトの種類によって、異なる処理が動く |
| オーバーライド | 子クラスが、親クラスのメソッドを、同じ名前で作り直す |
| オーバーロード | 同じ名前で、引数の違うメソッドを複数持つ |

### 多相性（令6秋で「低い」）
- 呼び出す側は、「親クラス（またはインタフェース）」のメソッドを呼ぶ。実際に動く処理は、渡されたオブジェクトの種類で決まる。
- 利点: 新しい種類を追加するとき、呼び出す側のコードを変えなくてよい（変更に強い）。
- 設問では、「どのクラスのどのメソッドが動くか」を、継承関係の図と、インスタンスの作成箇所から読む。

### 既存クラスへの最小限の追加（令6秋 3(1)で「低い」）
- 既存のコードをなるべく変えない（開放閉鎖の原則: 拡張に対して開き、修正に対して閉じる）。
- 方法の例: 継承で新しいクラスを作る／インタフェースを実装した新しいクラスを足す／共通の処理は、親クラスに置く。

## 2. UML（令6春、令3春）

| 図 | 表すもの | 読みどころ |
|---|---|---|
| クラス図 | クラスと、その関係 | 関連、汎化（継承）、集約、コンポジション、依存 |
| シーケンス図 | オブジェクト間の、メッセージの時間順のやり取り | 縦が時間。矢印が、メソッド呼出し。戻りは破線 |
| 状態機械図（状態遷移図） | 状態の変化 | イベント、条件、アクション |
| アクティビティ図 | 処理の流れ（分岐、並行） | 業務や処理の手順 |
| ユースケース図 | システムの利用者と、機能 | 利用者の視点 |

### クラス図の関係の記号
| 関係 | 意味 | 覚え方 |
|---|---|---|
| 汎化（継承） | 子が親の特殊化。白抜き三角の矢印が親へ | 「〜は〜の一種」 |
| 関連 | 長期的な関係。線で結ぶ | 「〜は〜を持つ・知っている」 |
| 集約 | 全体と部分。部分は独立して存在できる（白抜きひし形） | 「ゆるい所有」 |
| コンポジション | 全体と部分。部分は全体と運命を共にする（黒塗りひし形） | 「強い所有」 |
| 依存 | 一時的な利用。点線の矢印 | 「引数や変数で使う」 |

- 令6春 6（低い）: オブジェクト間の関係とメソッド呼出しの流れ。クラス図で「誰が誰を知っているか」を読み、シーケンス図の矢印の向きに対応させる。

## 3. デザインパターン（令6春、令3春）

| パターン | 目的 | 覚え方 |
|---|---|---|
| Observer | 1つの対象の状態変化を、依存する複数のオブジェクトに、自動で通知する | 「購読（通知を受ける）」 |
| Strategy | 処理のアルゴリズムを、部品として入れ替えられるようにする | 「やり方の差し替え」 |
| Factory Method | オブジェクトの生成を、サブクラスに任せる | 「作り方を隠す」 |
| Singleton | インスタンスを、1つだけにする | 「唯一」 |
| Adapter | 互換性のないインタフェースを、変換してつなぐ | 「変換アダプタ」 |
| Facade | 複雑な内部を、単純な窓口で隠す | 「受付窓口」 |
| Template Method | 処理の骨組みを親に、詳細を子に任せる | 「ひな形」 |
| Decorator | 既存のオブジェクトに、機能を重ねて追加する | 「飾りを足す」 |
| Composite | 個と集まりを、同じように扱う | 「入れ子（ファイルとフォルダ）」 |

### Observerパターン（令6春）
- 登場人物: Subject（通知する側。状態を持つ）、Observer（通知を受ける側）
- 流れ: Observerが、Subjectに「登録（attach）」しておく → Subjectの状態が変わる → Subjectが、登録済みの全Observerに「通知（notify）」する → 各Observerが、「更新（update）」を行う
- 利点: 通知する側は、相手の具体的な種類を知らなくてよい（抽象化、疎結合）。通知先の追加・削除が簡単。
- ダッシュボードの例: データが更新されると、複数のグラフが、それぞれ再描画される。

## 4. 並行処理・スレッド（令5秋、令3春）

### 基本用語
| 用語 | 内容 |
|---|---|
| プロセス | OSが管理する、実行中のプログラム。独自のメモリ空間を持つ |
| スレッド | プロセス内の、実行の流れ。メモリを共有する |
| マルチスレッド | 複数のスレッドで、並行に処理する |
| メインスレッド（UIスレッド） | 画面の操作を担当する。時間のかかる処理を置くと、画面が固まる |
| join | 別のスレッドの終了を、待ち合わせる |
| 排他制御（ロック、ミューテックス） | 共有データを、同時に書き換えさせない |
| デッドロック | 互いに相手の資源を待って、止まる |
| コンテキストスイッチ | 実行する処理を切り替えるとき、状態を保存・復元する作業 |

### スマホアプリでのスレッドの使い分け（令5秋で「低い」）
- 原則: 通信、ファイル読込み、重い計算など、時間のかかる処理は、別のスレッド（バックグラウンド）で行う。画面の更新は、UIスレッドで行う。
- 処理内容（画面、通信、計算）に応じて、どのスレッドに任せるかを、本文から決める。
- join: メインの処理が、別スレッドの結果を使うときに、その終了まで待つ。待たずに先へ進むと、結果が未完成のまま使われる。

### コンテキストスイッチとスレッドスイッチ（令3春 設問1(2)で「低い」）
- IPA講評: 「コンテキストスイッチ」を問うたのに、「スレッドスイッチ」と答える誤答が多かった。コンテキストスイッチは、1つのCPUコアを有効に使うために、プロセスやスレッドを切り替える処理（用語として覚える）。
- プロセス間の切替えは、メモリ空間の切替えを伴うので、負荷が大きい。
- スレッド間の切替えは、メモリを共有するので、プロセス間より軽い。
- 切替えが多すぎると、本来の処理に使う時間が減る。

### ノンブロッキングI/O（令3春）
- 通信や読込みの完了を待つ間、スレッドを止めずに、別の処理を進める方式。
- 少ないスレッドで、多くの接続を扱える。

## 5. Gitとブランチ運用（令5春）

### 基本の操作
| 操作 | 内容 |
|---|---|
| commit | 変更を、履歴に記録する |
| branch | 開発の流れを分ける |
| merge | 別のブランチの変更を、取り込む |
| rebase | ブランチの土台を付け替えて、履歴を一本にする |
| revert | 過去のコミットを「打ち消す新しいコミット」を作る（履歴は消えない） |
| reset | 履歴を、過去の時点へ戻す（共有済みの履歴には、使わない） |
| cherry-pick | 特定のコミットだけを、別のブランチへ取り込む |
| pull request（マージリクエスト） | 変更を、レビュー・承認してから、取り込む依頼 |

### 典型的なブランチ運用（Git-flow系）
| ブランチ | 役割 |
|---|---|
| main（master） | 本番にリリースした状態 |
| develop | 開発の統合先 |
| feature | 機能ごとの開発 |
| release | リリース前の調整 |
| hotfix | 本番の緊急修正 |

### 令5春で「低い」とされた型
- 変更を打ち消す操作の順序（設問3）: IPA講評は、複数の変更を打ち消す操作で、操作の順序の理解不足による誤答が多かった、とする。変更の内容だけでなく、変更が加えられた順番を意識する。図のコミットの並びに、操作を順に当てはめる。
  - 一般知識: 共有済みのコミットの取消しにはrevertを使い、履歴を書き換えるresetは共有済みのブランチでは避ける（講評の記述ではない）。
- どのブランチに、いつ操作するか（設問5、低い）: IPA講評は、複数の開発者が関わるときは、ブランチの役割を逸脱せず、どのタイミングでどのブランチに操作するかを正しく判断すること、とする。一般的なGit-flowの例: 本番の緊急修正は、mainから分岐したhotfixで修正し、mainとdevelopの両方へ戻す。リリース準備は、developから分岐したreleaseで行う。ブランチの役割（上の表）と、図の分岐元・取込み先を、1つずつ対応づける。

## 6. 設計・品質の判断（令7秋、令7春、令3秋ほか）

### 画面・UI設計（令7秋）
- テーブル型コンポーネント（一覧表）の設計要素: 表示する列、並べ替え、絞込み（フィルタ）、ページング、1ページの件数、更新のタイミングなど。利用者が、探す・比べる作業を、どうするかで決める。
- モバイル通信の帯域を意識した設計（令7秋で「低い」）
  - 一度に取得するデータ量を減らす（ページング、必要な項目だけを取得、画像の圧縮）
  - 通信の回数を減らす（まとめて取得、キャッシュ）
  - 通信が不安定でも使える（再試行、途中までの結果の表示）
- レスポンシブデザイン（平31春）: 画面幅に応じて、レイアウトを切り替える。1つのHTMLで、PCとスマホに対応できる。ただし、画面ごとの検証の工数が増え、コストが上がる要因になる。

### エラーハンドリング・監視（令7春）
| 種類 | 内容 | 対応 |
|---|---|---|
| 業務エラー | 入力の誤りなど、利用者の操作・業務ルールの問題 | 利用者に、原因と対処を表示する |
| システムエラー | 通信、サーバ、バグなどの異常 | 詳細はログに残し、運用担当者に通知。利用者には、簡潔な案内 |

- システムエラーの監視設計では、「何を検知して、誰に、どう知らせるか」を決める。
- 令7春 3（やや低い。IPA講評の要約）: システムの機能や挙動に影響を与えずに、異常や状態変化を捉える情報源（ログなど）を選ぶ。
- 「関連情報を誰が参照し得るか」（令7春 5(2)）: アクセス権の設計。役割ごとに、見える範囲を、本文の条件から整理する。

### データ連携（令4春で「低い」）
- ファイル連携（FTPなど）の構成: ヘッダーレコード（件数、日付など）、データレコード、トレーラレコード（件数の合計など）。
- 欠落の確認: ヘッダー（またはトレーラ）の件数と、実際に受け取ったデータの件数を、比較する。
- 取得できなかった場合: 前回の取得結果を表示する、取得できなかったことを利用者に知らせる、再取得する、などを、本文の要件に合わせて決める。
- 文字コード、区切り文字、桁数など、形式の取決めも、連携の前提になる。

### データ中心設計（令3秋で「低い」）
- 性能と変更容易性のトレードオフ
  - 正規化を進める → 重複がなく、変更しやすい。ただし、結合が増え、検索が遅くなることがある
  - 非正規化（あえて重複を持つ）→ 検索は速い。ただし、更新が複数箇所になり、整合性の維持が必要
- テーブル追加時のリリースリスク（令3秋 設問4(1)、低い）: IPA講評は、ソースコードの変更はテスト環境で十分にテストできるが、テーブル追加作業は、リリース時の限られた時間内で作業とテストを行う必要があるので、リスクが高い、とする。
  - 一般知識: 既存のデータの移行、既存プログラムへの影響、切戻しの難しさも考える。
- 令3秋 設問3(1)（低い）: 性能と変更容易性のトレードオフでは、本文の条件から、性能に重点を置く設計を選ぶ（アクセス数、機能変更の頻度を考慮）。

### 信頼性設計（令元秋）
| 考え方 | 内容 |
|---|---|
| フェールセーフ | 故障したときに、安全な側に倒す（信号機が全方向赤など） |
| フールプルーフ | 人が誤操作しても、事故にならない |
| フォールトトレラント | 一部が壊れても、全体として動き続ける（二重化） |
| フォールトアボイダンス | 故障しにくい部品を使う |

### 設計レビューと品質評価（令4秋）
- UCL／LCL、集合ミーティングの目的は、`../09_pm/05_quality_change.md` を参照。
- 集合ミーティングでは、欠陥の「指摘」に集中する。修正方法の議論は、別に行う。

## 8. 確認問題

- 先に自分で選んでから ▶を開く対象はこのファイルの内容だけ

**問1** 親クラスのメソッドを呼び出しても、実際のオブジェクトの種類によって、異なる処理が動く性質はどれか。
ア カプセル化　イ 多相性（ポリモーフィズム）　ウ 継承　エ オーバーロード

<details><summary>答えと解説</summary>
イ。新しい種類を追加するとき、呼び出す側のコードを変えなくてよい。エのオーバーロードは、同じ名前で、引数の違うメソッドを複数持つこと。
</details>

**問2** クラス図で、「部分は全体と運命を共にする」強い所有を表す関係はどれか。
ア 集約　イ コンポジション　ウ 依存　エ 汎化

<details><summary>答えと解説</summary>
イ。コンポジションは黒塗りひし形。アの集約は、部分が独立して存在できる、ゆるい所有（白抜きひし形）。ウは一時的な利用（点線の矢印）、エは継承。
</details>

**問3** 1つの対象の状態変化を、依存する複数のオブジェクトに、自動で通知するデザインパターンはどれか。
ア Strategy　イ Observer　ウ Singleton　エ Facade

<details><summary>答えと解説</summary>
イ。Observerが、Subjectに登録（attach）しておき、Subjectの状態が変わると、登録済みの全Observerに通知（notify）する。アはアルゴリズムの差し替え、ウはインスタンスを1つだけにする、エは複雑な内部を単純な窓口で隠す。
</details>

**問4** コンテキストスイッチの負荷について、適切なものはどれか。
ア プロセス間の切替えは、メモリ空間の切替えを伴うので、スレッド間より負荷が大きい　イ スレッド間の切替えは、プロセス間より負荷が大きい　ウ どちらも同じ負荷　エ 切替えに負荷はかからない

<details><summary>答えと解説</summary>
ア。スレッドはメモリを共有するので、切替えはプロセス間より軽い。切替えが多すぎると、本来の処理に使う時間が減る。IPA講評では、「コンテキストスイッチ」を問うたのに「スレッドスイッチ」と答える誤答が多かった（令3春 設問1(2)）。
</details>

**問5** すでに共有したブランチで、過去のコミットを取り消すときに適した操作はどれか。
ア reset　イ revert　ウ rebase　エ cherry-pick

<details><summary>答えと解説</summary>
イ。revertは、過去のコミットを「打ち消す新しいコミット」を作る操作で、履歴は消えない。resetは、履歴を過去の時点へ戻す操作なので、共有済みのブランチでは避ける（これは、講評ではなく一般知識）。
</details>

**問6** Git-flow系のブランチ運用で、本番の緊急修正はどのように行うか。
ア developから分岐したhotfixで修正し、mainだけに戻す　イ mainから分岐したhotfixで修正し、mainとdevelopの両方へ戻す　ウ releaseで修正し、featureへ戻す　エ featureで修正し、mainに直接戻す

<details><summary>答えと解説</summary>
イ。一般的なGit-flowの例。リリース準備は、developから分岐したreleaseで行う。ブランチの役割と、図の分岐元・取込み先を、1つずつ対応づける。
</details>

**問7** 人が誤操作しても、事故にならないようにする設計の考え方はどれか。
ア フェールセーフ　イ フールプルーフ　ウ フォールトトレラント　エ フォールトアボイダンス

<details><summary>答えと解説</summary>
イ。アのフェールセーフは、故障したときに安全な側に倒す（信号機が全方向赤など）。ウは、一部が壊れても全体として動き続ける（二重化）。エは、故障しにくい部品を使う。
</details>
