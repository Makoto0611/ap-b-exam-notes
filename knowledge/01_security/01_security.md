# 問1 情報セキュリティ（必須）の知識メモ

過去問の本文は載せない。用語・仕組み・出題の観点だけを書く。
出題テーマは `../../past-topics/01_security.md`。内容は一般知識が中心。「低い」「高い」などの評価の記述は、IPA講評の原文（PDF）と照合済み（2026-11-15）。

## 1. 基本の考え方

### 情報セキュリティの3要素（令6秋）
| 要素 | 意味 | 破られる例 |
|---|---|---|
| 機密性 | 許可された人だけが情報にアクセスできる | 情報漏えい |
| 完全性 | 情報が正確で、改ざんされない | データの書換え |
| 可用性 | 必要なときに使える | サービス停止、ランサムウェア |

- 設問で「どの要素への対策か」を問われたら、守りたいものが「見られない」「書き換えられない」「使える」のどれかで決める。
- 対策の目的を取り違えない（令2秋）。例: 誤送信対策は意図しない相手への送信を防ぐ／不正持ち出し対策は意図して持ち出す内部者を防ぐ。

### ハッシュ値の用途（令6秋）
- 同じデータからは同じ値、少しでも違えば全く違う値。元のデータには戻せない（一方向）。
- 用途: 改ざん検知（完全性の確認）、パスワードの保存（平文を持たない）、電子署名の効率化。

### 境界型防御とゼロトラスト（令6春）
| 方式 | 考え方 |
|---|---|
| 境界型防御 | 社内ネットワークの内側は信頼し、境界（ファイアウォールなど）で守る |
| ゼロトラスト | 内側も信頼しない。すべてのアクセスを、利用者・端末・状況で都度検証し、最小権限だけ許す |

- リモートワークやクラウド利用が増えると、境界が曖昧になり、境界型防御だけでは足りない。それがゼロトラストの背景。
- 出題の観点: 「社内にいること」ではなく「認証・認可を毎回確認する」ことが特徴。

## 2. 認証とパスワードへの攻撃（平31春、令7春）

| 攻撃 | 内容 | 対策 |
|---|---|---|
| ブルートフォース（総当たり） | 1つのIDに、パスワードを次々と試す | 入力回数の制限、アカウントロックアウト、多要素認証 |
| 辞書攻撃 | よく使われる語の一覧で試す | 推測されやすいパスワードを禁止 |
| リバースブルートフォース | 1つのパスワードを固定し、IDを変えて試す | 後述 |
| パスワードリスト攻撃 | 他サービスから漏れたIDとパスワードの組を試す | パスワードの使い回し禁止、多要素認証 |
| レインボーテーブル攻撃 | ハッシュ値から元のパスワードを逆引きする表を使う | ソルトの付加 |

### リバースブルートフォースでロックアウトが効かない理由（令7春で「低い」）
- ロックアウトは、「同じアカウントで失敗が続く」ことを数える。
- リバースブルートフォースは、アカウントごとの失敗が1〜数回しかなく、基準に達しない。
- 検知のしかた: 同じ送信元から、多くのアカウントへの失敗が出ていることを見る（送信元ごとの制限、ログの相関分析）。

### 入力回数制限の副作用（平31春）
- 制限を超えたらアカウントをロックすると、他人のIDを狙って何度も失敗させ、本人が使えなくする攻撃（アカウントロックアウトによる妨害）に使われる。
- ブルートフォース対策としては有効だが、リバースブルートフォースには効かない。

### ソルトとストレッチング（平31春で「低い」）
- ソルト: パスワードに、利用者ごとのランダムな値を付けてからハッシュ化する。
  - 同じパスワードでも、ハッシュ値が異なる
  - あらかじめ作ったレインボーテーブルが使えない
- ストレッチング: ハッシュ化を何千回も繰り返し、1回の試行を遅くする。総当たりに時間がかかる。
- ソルトは秘密にする必要はない（漏えいしても、各ユーザー個別の計算が必要になる点が重要）。
- IPA講評（平31春 設問3(2)）: ソルトの付加でパスワード（ハッシュ化する値）の桁数が大きくなり、レインボーテーブルの作成が困難になる。

### 認証に使う情報
| 要素 | 例 |
|---|---|
| 知識 | パスワード、暗証番号 |
| 所持 | ICカード、スマホ、ワンタイムパスワード |
| 生体 | 指紋、顔 |

- 認証に適さない情報: 他人に知られやすい情報（氏名、生年月日、メールアドレス）。
- IPA講評（平31春 設問1(1)a、低い）: 「パソコンの製造番号」は、真正性（本人のものか）を検証できないので、認証の対象に適さない。パソコンが利用者の所有物でも、認証に使えるとは限らない。
- 多要素認証: 異なる種類を2つ以上組み合わせる（知識＋知識は多要素ではない）。

## 3. ログと検知（令6春、令5春、令4春）

| 用語 | 内容 | 覚え方 |
|---|---|---|
| ログ | 機器・システムの操作や通信の記録 | 事後の調査と検知の材料 |
| SIEM | 複数の機器のログを集め、相関分析して、不審な事象を検知・通知する仕組み | 「ログを集めて、つなげて、見つける」 |
| EDR | パソコンなど端末（エンドポイント）の挙動を監視し、不審な動きを検知して、隔離などの対応を支援する | 「侵入された後」を見つけて対処する |
| EPP | 端末への侵入を、事前に防ぐ（ウイルス対策ソフトなど） | 「入れない」 |
| IDS／IPS | 通信を監視して不正を検知する／検知して遮断する | IPSは遮断まで行う |
| WAF | Webアプリへの攻撃（SQLインジェクションなど）を防ぐ | Web専用のファイアウォール |

- SIEMの役割（令4春 設問4(5)、低い）: IPA講評は、ログを統合管理し、ログの相関分析をリアルタイムに行うことで、インシデントの早期検知や分析時間の短縮ができる仕組み、としている。個別の機器では見えない、複数のログにまたがる不審な動きを発見する。
- EDRの仕組みと効果（令5春）: 端末の挙動を記録し続け、既知のマルウェアのパターンに合わない未知の攻撃でも、不審な挙動で検知できる。感染した端末をネットワークから切り離す対応が早くなる。
- 設問では、ログ「の収集・保存」が目的なのか、ログ「の分析による検知」が目的なのかを区別する。

### 不要なサービスの停止（令4春 設問1、やや低い）
- 使っていないサービスやポートは、攻撃の入口になる。IPA講評は、最低限必要なものを除いて停止する対策が重要としている。止めることで、攻撃対象（攻撃面）を減らす。

## 4. 暗号と証明書（令5秋、令3春）

### 共通鍵暗号と公開鍵暗号
| 項目 | 共通鍵暗号 | 公開鍵暗号 |
|---|---|---|
| 鍵 | 暗号化と復号で同じ鍵 | 公開鍵と秘密鍵のペア |
| 処理の速さ | 速い | 遅い（処理が複雑） |
| 課題 | 鍵を安全に相手に渡す方法（鍵配送問題） | 公開鍵が本人のものか確認する方法 |
| 代表 | AES | RSA、楕円曲線暗号 |

- ハイブリッド暗号: 本文は速い共通鍵で暗号化し、その共通鍵を、相手の公開鍵で暗号化して渡す。両方の長所を使う。
- 令5秋 2(3)（低い）: 処理の違い。公開鍵暗号は計算量が多いので、大きなデータの暗号化には共通鍵を使う。

### 電子署名（S/MIMEなど）
| 目的 | 使う鍵 |
|---|---|
| 暗号化（機密性） | 受信者の公開鍵で暗号化 → 受信者の秘密鍵で復号 |
| 電子署名（本人性・完全性） | 送信者の秘密鍵で署名 → 受信者が送信者の公開鍵で検証 |

- 電子署名で、「誰が作ったか（なりすましでない）」「改ざんされていないか」が確認できる。
- 署名は、メッセージ全体ではなく、ハッシュ値に対して行うのが一般的。

### 電子証明書
- 公開鍵が、本当にその人（サーバ、組織）のものであることを、認証局（CA）が保証する書類。
- 確認する項目: 有効期限、発行者（信頼できるCAか）、失効していないか、サブジェクト（誰のものか）。
- 証明書の電子署名が本物かどうかの検証には、CA（認証局）の公開鍵を使う（令5秋 3。IPA講評の要約）。
- 証明書の種類（令3春で「低い」）

  | 種類 | 審査 |
  |---|---|
  | DV証明書 | ドメインの管理権限だけを確認する（組織の実在は審査しない） |
  | OV証明書 | ドメイン＋組織の実在を確認する |
  | EV証明書 | 組織の実在を、さらに厳格に確認する |

- DVは、悪意のあるサイトでも取得できるため、「HTTPSの鍵マーク＝安全なサイト」とは言えない。
- IPA講評（令3春 設問3(2)）: 近年はDV証明書の入手が容易になったので、Webサイトの信頼性を高めるためにEV証明書を使うことも多い。DVとEVの違いと、EVで実現できる対策を理解する。

## 5. メールのセキュリティ（令5秋、令元秋）

### PPAP（令5秋）
- 暗号化したZIPファイルをメールで送り、別のメールでパスワードを送る方式。
- 問題点
  - パスワードを、同じ経路（同じメール）で送っているので、盗聴者は両方を入手できる
  - 暗号化されたZIPは、メールゲートウェイのマルウェア検査ができない（検査を回避できてしまう）
  - 暗号の強度が弱い方式がある
  - 受信者が、ファイル展開のたびに手間がかかる
- 代替: S/MIME、ファイル共有サービス、クラウドストレージの共有リンク

### 送信ドメイン認証（令元秋で「低い」）
| 方式 | 内容 |
|---|---|
| SPF | 送信元のIPアドレスが、そのドメインが許可したサーバのものかを、DNSの情報で確認する |
| DKIM | 送信サーバが付けた電子署名を、DNSの公開鍵で検証し、改ざんと送信ドメインを確認する |
| DMARC | SPFとDKIMの結果を使って、失敗したメールをどう扱うか（拒否、隔離、何もしない）を、ドメイン所有者が指定する |

- 目的: 送信者を偽装した（なりすましの）メールを見分ける。

### 標的型攻撃（令元秋）
- 標的型メール: 特定の組織・個人に、業務に関係がありそうな文面で送る。添付ファイルやリンクでマルウェアに感染させる。
- 水飲み場攻撃: 標的がよく見るWebサイトを改ざんし、アクセスした標的を感染させる。メールを送らない。
- 初動対応: 感染が疑われる端末は、ネットワークから切り離す（LANケーブルを抜く）。電源は切らない（メモリ上の証拠が消える）。

## 6. 不正・内部不正への対策（令7秋、令2秋）

### 不正のトライアングル（令7秋で「やや低い」）
不正が起きる3つの条件。

| 要因 | 意味 | 対策 |
|---|---|---|
| 動機・プレッシャー | 不正をしたくなる事情（金銭、不満） | 労務環境の改善、相談窓口 |
| 機会 | 不正ができる状況 | アクセス制御、職務分離、ログ記録、監視 |
| 正当化 | 「やってもよい」と自分を納得させる | 教育、規程、不正の通知（罰則の周知） |

- 出題の観点: 技術的な対策（検知、制御）は「機会」に効く。正当化や動機への対策（教育、組織風土）を、設問が求めていることがある。

### 対策の告知が不正の抑止になる理由（令2秋）
- 「監視している」「ログを取っている」と知らせると、発覚するリスクが高いと考え、不正をやめる。つまり、機会が減ると感じさせる。

### デジタルフォレンジックス（令2秋）
- 不正や事故の調査のために、ログ、ディスク、メモリなどの証拠を、改ざんされないように保全・分析する。
- 目的: 原因の究明、被害範囲の特定、法的な証拠としての利用。
- 保全の考え方: 元の媒体は触らず、複製したものを調べる。ハッシュ値で、改ざんされていないことを示す。

## 7. 物理セキュリティ（令3秋）

| 用語 | 意味 |
|---|---|
| クリアデスク | 離席時に、机の上に書類を放置しない |
| クリアスクリーン | 離席時に、画面に情報を表示したままにしない（画面ロック） |
| 入退室管理 | ICカード、生体認証で、入室者を管理・記録する |
| 共連れ（ピギーバック）対策 | 認証された人に続いて、別の人が入ることを防ぐ（フラッパーゲートなど） |
| 私物持込みの対策 | 私物のUSBメモリ、スマホ、カメラの持込みを制限する。許可する場合は、持ち込んだ物が不正につながらない物だと、周囲が判別できるようにする（令3秋 設問3(4)d、平均的） |

- Common Criteria（ISO/IEC 15408）: IT製品のセキュリティ機能が、仕様どおりに実装されていることを、第三者が評価・認証する国際基準（令3秋で「低い」）。
- クリアスクリーンの目的: 離席中に、他人が画面を見たり、操作したりすることを防ぐ。

## 8. ネットワークとDNS（令4秋、令3春）

### ICMP（令4秋）
- ICMPは、ネットワークの状態を調べたり、エラーを通知したりするためのプロトコル。pingは、ICMPエコー要求（Echo Request）を送り、エコー応答（Echo Reply）が返ってくるかで、通信できるかを調べる。
- IPA講評（令4秋）: ICMPエコー要求パケットにはポート番号は含まれず、宛先IPアドレスのホスト自体が稼働しているかを判断するために使う（設問2(1)、やや低い）。エコー要求の連続送信は、業務処理による通信ではなく、本文に書かれたマルウェアの侵入後の活動によるものだと導く（設問3(1)、低い）。
- 攻撃の例: 大量のICMPを送って負荷をかける。通常の業務通信と違い、同じ宛先に連続して、小さなパケットを決まった間隔で送る、などの特徴が出る。
- 設問では、「業務の通信」と「不審な通信」を、本文の通信ログ・表から区別する。区別の手がかり（送信間隔、サイズ、宛先、回数）を、本文から探す。

### DNSへの攻撃（令3春）
| 攻撃 | 内容 | 対策 |
|---|---|---|
| キャッシュポイズニング | キャッシュサーバに、偽の応答を覚えさせ、偽のサイトへ誘導する | DNSSEC、送信元ポートのランダム化 |
| DNS水責め（ランダムサブドメイン攻撃） | 存在しないランダムなサブドメインを大量に問い合わせ、権威サーバを過負荷にする | 問合せの制限、キャッシュサーバの対策 |
| DNSアンプ攻撃 | 小さな問合せで、大きな応答を、被害者宛に出させる | オープンリゾルバにしない |

## 9. マルウェアとバックアップ（令5春、令7春）

### ランサムウェアと対策
- 感染すると、データを暗号化して身代金を要求する。最近は、データを盗んで公開をちらつかせる「二重脅迫」も多い。
- 対策: 脆弱性への対応、EDR、メールの検査、権限の最小化。
- バックアップ: 攻撃者が、ネットワーク上のバックアップも暗号化してしまう。
  - オフライン（ネットワークから切り離す）のバックアップ
  - 書換え不可のストレージ（WORM、イミュータブル）: 一度書いたデータを、一定期間変更・削除できない（令7春で「低い」）
  - バックアップ用アカウントを、通常の管理者と分ける

### サプライチェーン攻撃（令7秋、令7春）
- 取引先、委託先、ソフトウェアの更新元など、「弱い部分」を経由して、本来の標的に侵入する。
- 対策: 取引先のセキュリティ要件の確認、更新ファイルの署名確認、脆弱性情報の迅速な収集と対応、ソフトウェア部品表（SBOM）。

### ペネトレーションテスト（令6秋）
- 攻撃者の視点で、実際に侵入を試み、脆弱性を確認する。
- 脆弱性診断は、既知の脆弱性を網羅的に探す（侵入までは行わない）。

## 10. 解き方メモ

1. 設問の聞き方を決める: 「何を守るためか（3要素）」「誰の（外部の攻撃者／内部者）」「技術対策か、人・組織の対策か」
2. 認証・パスワードの攻撃は、「何を固定して、何を変えて試すか」で区別する（ブルートフォース=ID固定、リバース=パスワード固定）
3. 暗号・署名は、「誰の、どの鍵で」を毎回書く（暗号化=受信者の公開鍵、署名=送信者の秘密鍵）
4. 対策の設問は、本文の状況に合わせて書く（一般論だけで終わらない）
5. 令7秋の不正のトライアングルのように、技術対策に偏らず、人の心理に効く対策も考える
