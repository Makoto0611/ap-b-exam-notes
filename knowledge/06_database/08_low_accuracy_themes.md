## 1. ACID特性と、デッドロックとの区別（低い。平26秋）

### 要点
- トランザクションが守るべき4つの性質（ACID）
  - 原子性（Atomicity）: 全部実行されるか、全く実行されないか。
  - 一貫性（Consistency）: 実行の前後で、データの整合性が保たれる。
  - 隔離性（Isolation）: 同時に実行しても、互いに影響しない（1つずつ実行したのと同じ結果）。
  - 耐久性（Durability）: コミットした結果は、障害が起きても失われない。

### 解説
- 平26秋の講評は、設問1（ACIDの理解）でbの正答率が低かった、設問4(1)で「デッドロック」と誤答した受験者が多かった、と述べている。設問の内容は講評に書かれていないので、原文の問題で確かめること。
- デッドロック: 複数のトランザクションが、互いに相手の持つロックの解放を待って、進めなくなる状態。ロックが原因で起こる、別の現象。ACIDの性質ではない。
- 複数のDBを更新するトランザクションでは、全てのDBで更新を成功させるか、全て取り消す必要がある。その代表が、2相コミット（準備→コミットの2段階）。（一般知識）

### 確認問題
**問1** 「口座Aから口座Bへの送金で、引き落としだけが実行され、入金が実行されない状態にならない」ことを保証する性質はどれか。
ア 原子性　イ 一貫性　ウ 隔離性　エ 耐久性

<details><summary>答えと解説</summary>
ア。複数の更新を、全部実行するか全く実行しないかにするのは、原子性。
</details>

**問2** コミットした更新が、直後の障害で消えないことを保証する性質はどれか。
ア 原子性　イ 一貫性　ウ 隔離性　エ 耐久性

<details><summary>答えと解説</summary>
エ。ログなどを使って、コミット済みの更新を復元できるようにする。
</details>

**問3** デッドロックの説明として、適切なものはどれか。
ア 2つのトランザクションが、互いに相手のロックの解放を待って、進めなくなる　イ トランザクションが、途中で取り消される　ウ コミット後にデータが失われる　エ 同じ行を、別のトランザクションが読めない状態が一瞬続く

<details><summary>答えと解説</summary>
ア。エは普通のロック待ちで、待てば解消する。デッドロックは、待っても解消しない。
</details>

## 2. 正規化、第二正規形、代用キー（低い。平21秋、平27秋、平29秋）

### 要点
- 第1正規形: 繰返しの項目をなくす（1つのセルに1つの値）。
- 第2正規形: 主キーの一部だけで決まる項目（部分関数従属）を、別の表に分ける。
- 第3正規形: 主キー以外の項目で決まる項目（推移的関数従属）を、別の表に分ける。
- 代用キー: 業務上の意味を持たない連番などを、主キーにしたもの。

### 解説
- 主キーが1つの列だけなら、主キーの「一部」がないので、部分関数従属は起きない。このとき、第1正規形であれば、自動的に第2正規形になる。（「第二正規形でなくても問題が起きない理由」を考えるときの手がかり。平21秋の講評では、設問2(1)の正答率が低かった。原文の設問は確かめること）
- 複合主キー（例: 注文番号と商品コード）の表で、商品名が商品コードだけで決まるなら、商品名は別の表に分ける。分けないと、同じ商品名が何度も入る（更新の矛盾が起きる）。
- 代用キーを使う理由の例: 複合キーが長い、元のキーの値が変わりうる、履歴を管理したい。（一般知識）

### 確認問題
**問1** 表「注文明細（注文番号、商品コード、商品名、数量）」。主キーは（注文番号、商品コード）。商品名は商品コードだけで決まる。第2正規形にするには、どうするか。
ア 商品名を、別の表（商品コード、商品名）に分ける　イ 数量を、別の表に分ける　ウ 注文番号を、削除する　エ 主キーを、数量にする

<details><summary>答えと解説</summary>
ア。主キーの一部（商品コード）だけで決まる項目（商品名）は、別の表に分ける。
</details>

**問2** 主キーが「社員番号」1列だけの表がある。繰返しの項目がない。この表の正規形について、適切なものはどれか。
ア 部分関数従属は起きないので、第2正規形を満たす　イ 必ず第3正規形を満たす　ウ 第1正規形ではない　エ 正規形とは無関係

<details><summary>答えと解説</summary>
ア。主キーが1列なら、主キーの一部で決まる項目は存在しない。第3正規形かどうかは、別に確認が必要（推移的関数従属があるかもしれない）。
</details>

## 3. NULLとIS NULL、外部結合（低い。平27秋、平28春、令5春）

### 要点
- NULLは「値がない」状態。値としての比較では、等しいかどうかを、判断できない。
- NULLかどうかは、`= NULL` ではなく、`IS NULL` で調べる。
- 外部結合: 片方の表にしかない行も、結果に残す。

### 解説
- `WHERE 列 = NULL` は、常に結果が「不明」になって、行が1行も選ばれない。`WHERE 列 IS NULL` を使う。
- LEFT OUTER JOIN: 左の表の全ての行を残す。右の表に、一致する行がなければ、右の列はNULLになる。
- 「右の表に対応する行がない、左の行」を探すときは、LEFT OUTER JOINした後に、右の表の主キーが `IS NULL` の行を選ぶ。
- 注意: LEFT OUTER JOINの後に、WHERE句で右の表の列に値の条件を付けると、NULLの行が消えて、内部結合と同じ結果になる。右の表の条件は、ON句に書く。（令5春の2(2)のLEFT OUTER JOIN、平28春の外部結合のキーワード欠落）

### 確認問題
**問1** 表「商品」のうち、「備考」が入っていない行を選ぶ文として、正しいものはどれか。
ア `SELECT * FROM 商品 WHERE 備考 = NULL`　イ `SELECT * FROM 商品 WHERE 備考 IS NULL`　ウ `SELECT * FROM 商品 WHERE 備考 = ''`　エ `SELECT * FROM 商品 WHERE 備考 <> NULL`

<details><summary>答えと解説</summary>
イ。NULLは、`IS NULL` で調べる。アとエは、常に行が選ばれない。
</details>

**問2** 表「顧客」と表「注文」がある。注文が1件もない顧客を探したい。適切な方法はどれか。
ア 顧客 LEFT OUTER JOIN 注文 して、注文の主キーが IS NULL の行を選ぶ　イ 顧客 INNER JOIN 注文 して、注文の主キーが IS NULL の行を選ぶ　ウ 注文 INNER JOIN 顧客 して、全ての行を選ぶ　エ 顧客と注文を、結合せずに UNION する

<details><summary>答えと解説</summary>
ア。左（顧客）の行を全て残し、右（注文）に対応する行がない顧客は、注文の列がNULLになる。イは、内部結合なので、対応する行がない顧客が、そもそも残らない。
</details>

## 4. 副問合せ、自己結合（低い。平25秋、平30秋）

### 要点
- 副問合せ: SELECT文の中に、別のSELECT文を書く。
  - 結果が1行1列のとき（スカラ副問合せ）: 比較の右辺などに使える。
  - 結果が複数行のとき: `IN` や `EXISTS` と組み合わせる。
- 自己結合: 同じ表を、別名を付けて2回使い、結合する。

### 解説
- 例（自己結合）: 社員表に、上司の社員番号の列がある。社員とその上司の名前を、並べて出す。

```
SELECT e.氏名, b.氏名
FROM 社員 e
INNER JOIN 社員 b ON e.上司番号 = b.社員番号
```

- 例（副問合せ）: 平均より高い単価の商品。

```
SELECT 商品名 FROM 商品
WHERE 単価 > (SELECT AVG(単価) FROM 商品)
```

- 副問合せの結果を、別の表のように結合して使う書き方もある（平25秋の講評は、副問合せを使ったSQLの正答率が低かった、と述べている）。

### 確認問題
**問1** 平均単価より高い商品を選ぶ文として、正しいものはどれか。
ア `SELECT 商品名 FROM 商品 WHERE 単価 > AVG(単価)`　イ `SELECT 商品名 FROM 商品 WHERE 単価 > (SELECT AVG(単価) FROM 商品)`　ウ `SELECT 商品名 FROM 商品 HAVING 単価 > AVG(単価)`　エ `SELECT AVG(単価) FROM 商品 WHERE 単価 > 商品名`

<details><summary>答えと解説</summary>
イ。WHERE句の中では、集計関数を直接使えない。副問合せで、先に平均を求める。
</details>

**問2** 自己結合で、同じ表を2回使うときに、必ず必要なものはどれか。
ア 別名（エイリアス）　イ GROUP BY　ウ ORDER BY　エ DISTINCT

<details><summary>答えと解説</summary>
ア。同じ表を区別するために、それぞれに別名を付ける。
</details>

## 5. ORDER BYと、集計の合計値（低い。平28春、平28秋）

### 要点
- ORDER BY: 並べ替え。ASCは昇順（省略したときもこちら）、DESCは降順。
- 複数の列を指定すると、左の列から順に並べて、同じ値の中を、次の列で並べる。
- 合計値: `SUM(列)` を `GROUP BY` と組み合わせる。

### 解説
- 例: 部署ごとの売上の合計を、多い順に並べる。

```
SELECT 部署, SUM(売上) AS 合計
FROM 売上表
GROUP BY 部署
ORDER BY 合計 DESC
```

- `GROUP BY` に書いていない列は、`SELECT` に、そのまま書けない（集計関数を使う）。

### 確認問題
**問1** 部署ごとの売上の合計を、多い順に並べる。空欄に入る語はどれか。
`SELECT 部署, SUM(売上) AS 合計 FROM 売上表 GROUP BY 部署 ORDER BY 合計 [　　]`
ア ASC　イ DESC　ウ DISTINCT　エ HAVING

<details><summary>答えと解説</summary>
イ。多い順は、降順（DESC）。
</details>

## 6. 権限の制御（GRANT）、関連の多重度、マスタの更新と履歴（低い。平30秋、平23秋、平29春）

### 6-1 権限の制御
- `GRANT 権限 ON 表 TO 利用者` で、利用者に権限を与える。
- 例: `GRANT SELECT ON 社員 TO 人事担当` は、社員表の参照だけを、人事担当に許可する。
- 列や行を限定して見せたいときは、ビュー（必要な列・行だけの仮想の表）を作り、そのビューに権限を与える。（一般知識）

**問1** 営業担当に、顧客表の参照だけを許可する文として、正しいものはどれか。
ア `GRANT SELECT ON 顧客 TO 営業担当`　イ `GRANT ALL ON 顧客 TO 営業担当`　ウ `GRANT UPDATE ON 顧客 TO 営業担当`　エ `REVOKE SELECT ON 顧客 FROM 営業担当`

<details><summary>答えと解説</summary>
ア。参照だけなので、SELECT権限。イは全ての権限、ウは更新、エは取り上げる。
</details>

### 6-2 関連の多重度（1対1、1対多）
- 1つの申請に、複数の明細が付くなら、申請と明細は「1対多」。明細を1つしか持てないと誤るのが、平23秋の誤答。
- 判断の方法: 「Aが1つ決まったとき、Bは何個あるか」「Bが1つ決まったとき、Aは何個あるか」の両方を考える。

**問2** 「1つの注文には、複数の商品を入れられる。1つの商品は、複数の注文に入る」。注文と商品の関係はどれか。
ア 1対1　イ 1対多　ウ 多対多　エ 関係なし

<details><summary>答えと解説</summary>
ウ。両方向とも「多」。多対多は、間に交差エンティティ（注文明細）を置いて、2つの1対多に分ける。
</details>

### 6-3 マスタの更新と履歴
- 単価などは、変わる。変わった後でも、過去の取引は、当時の単価で見られる必要がある。
- 対策の例: 取引の明細に、その時点の単価を、コピーして持つ。または、マスタに適用開始日と終了日を持たせて、履歴を残す。（一般知識。平29春の講評は、マスタの更新と履歴を考慮した設計の正答率が低かった、と述べている）

**問3** 商品マスタの単価を変更しても、過去の売上の金額が変わらないようにしたい。適切な設計はどれか。
ア 売上明細に、販売時点の単価を持たせる　イ 売上明細には単価を持たせず、常に商品マスタの最新の単価を参照する　ウ 商品マスタの単価を、変更できないようにする　エ 売上明細を、全て削除する

<details><summary>答えと解説</summary>
ア。最新の単価だけを参照すると、過去の売上の金額が、遡って変わってしまう。
</details>
