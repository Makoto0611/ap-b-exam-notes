# 総合問題 4題（定義・権限・検索・更新・設計を1つの場面で使う）

1行ずつの練習（`02_exercises.md`）は辞書として残し、ここでは**実務と同じように、複数の要素を同時に使う**。1題が1つの場面で、次の流れになっている。

1. 表を定義する（型・主キー・外部キー・DEFAULT・CHECK）
2. 権限を与える・列を追加する・ビューを作る
3. データを入れて、検索する（結合・集計・外部結合・副問合せ）
4. 更新する（複数の表を1つのトランザクションで）
5. 設計の問いに答える

試験の問6と同じく、**本文と条件表から、空欄に入るSQLを組み立てる**のが目的。目安は1題15〜20分。

## 進め方（1題ごと）
1. 条件表を読む。空欄の記号ごとに、「どの行を見るか」を先に決める（`../../../method/blank-filling-method.md` の4ステップ）
2. **A（定義）** を自分のファイル（例 `my_s1.sql`）に書いて実行する
   ```
   python3 sql.py -f my_s1.sql
   python3 sql.py -f 06_s1_data.sql        # データを入れる
   ```
3. **B（検索）・C（更新）** を `python3 sql.py repl` で試す。期待する結果は問題に書いてある
4. 答え合わせは `06_answers.sql`（記号が空欄と対応）。先に見ない

`GRANT` / `REVOKE` は SQLite にないので、書いて答えと見比べる。

> 他の題の表が残っていても問題ない。各題の表名は重ならない（答えのファイルは、先頭で `DROP TABLE IF EXISTS` している）。

## A 定義・権限・変更
```sql
CREATE TABLE equipment (
    equipment_id  CHAR(5)     NOT NULL,
    equipment_name  VARCHAR(30) NOT NULL,
    category    [ ア ],
    status    [ イ ],
    PRIMARY KEY (equipment_id)
);
CREATE TABLE loan (
    loan_id  INTEGER  NOT NULL,
    equipment_id  CHAR(5)  NOT NULL,
    employee_id  CHAR(4)  NOT NULL,
    loan_date  DATE     NOT NULL,
    return_date  [ ウ ],
    [ エ ],
    [ オ ],
    FOREIGN KEY (employee_id) REFERENCES employee (employee_id)
);
```
（課表・社員表も、同じ要領で自分で書いて作る。貸出表より先に作ること）

- **カ**: 総務課は、備品表の「備品ID・備品名・状態」だけを参照できる。GRANT文を書け
- **キ**: 既存の備品表に、50桁以内の可変長文字の列「備考」を追加する。ALTER文を書け
- **ク**: 貸出中（返却日が空）の貸出だけを、備品ID・社員ID・貸出日で見せるビュー「貸出中」を作れ

<details><summary>ヒント（詰まったら）</summary>

- ア・イ: 型 → 制約の順。DEFAULT は NOT NULL より前（`01_condition_to_sql.md`）
- ウ: 「空を許す」は、NOT NULL を**付けない**
- エ・オ: 条件表の「主キー」「〜を参照」の行。列を書く場所と、種類を書く場所を分ける
- カ: 列を絞るときは、権限名のあとに列名をかっこで書く
- ク: 検索の結果に名前を付けた表 → `CREATE VIEW 名前 AS SELECT ...`
</details>

## B 検索

- **サ**: 課ごとの**貸出中の件数**。貸出中がない課も 0 で出す（期待: general_affairs0・development2・sales0）

<details><summary>ヒント</summary>

- ケ: 社員と貸出を結合 → 返却日が空の行だけ → 社員ごとに数える → 2以上は集計の後に絞る
- コ: 備品を左にして結合し、右側の主キーが空の行を探す
- サ: 課 → 社員 → 貸出の順に、すべて左外部結合。**「返却日が空」の条件は、WHERE ではなく ON に書く**（WHERE に書くと、0件の課が消える）
</details>

## C 更新（複数の表を同時に）
- **シ**: 2026-11-15 に、備品 P0002 を社員 E004 に貸し出す（貸出ID は 6）。貸出表への追加と、備品表の状態の更新を、1つのトランザクションにまとめよ
- **ス**: 備品 P0001 を 2026-11-15 に返却する。**返却日が空の行だけ**を更新し、備品の状態も戻せ

<details><summary>ヒント</summary>

- ス: P0001 は過去にも貸し出されている。WHERE を備品IDだけにすると、返却済みの行も書き換わる
</details>

## D 設計の問い
1. 貸出表は、備品と社員の間の何にあたるか。主キーに「備品ID＋貸出日」ではなく貸出IDを使う理由は何か
2. 備品表の「状態」は、貸出表から導ける情報でもある。それでも持たせる利点と、持たせることで起きる問題は何か

<details><summary>考え方</summary>

1. 備品と社員の**多対多を解消する連関実体**。同じ備品を同じ日に返却して貸し直すと「備品ID＋貸出日」が重なるので、連番の代用キーにする
2. 利点: 在庫かどうかを、貸出表を調べずに読める。問題: 貸出表と状態がずれる（だから C は、同じトランザクションで更新する）
</details>

## 場面
顧客が注文し、1回の注文に複数の商品が入る。注文を取り消すと、その明細も一緒に消える。

## 条件表
| 表 | 列 | 条件 |
| --- | --- | --- |
| 顧客 | 顧客ID | 5桁の固定長文字。主キー |
| 顧客 | 顧客名、地域 | 可変長文字。空にできない |
| 商品 | 商品ID | 4桁の固定長文字。主キー |
| 商品 | 商品名 | 30桁以内の可変長文字。空にできない |
| 商品 | 単価 | 整数。空にできない。**0より大きい値**に限る |
| 注文 | 注文番号 | 整数。主キー |
| 注文 | 顧客ID | 5桁の固定長文字。空にできない。顧客表を参照 |
| 注文 | 注文日 | 日付。空にできない |
| 注文明細 | 注文番号、行番号 | 整数。**2列の組**で主キー。注文番号は注文表を参照し、**注文が消えたら明細も自動的に消える** |
| 注文明細 | 商品ID | 4桁の固定長文字。空にできない。商品表を参照 |
| 注文明細 | 数量 | 整数。空にできない。0より大きい値に限る |

## A 定義・権限
```sql
CREATE TABLE product (
    product_id  CHAR(4)     NOT NULL,
    product_name  VARCHAR(30) NOT NULL,
    unit_price    INTEGER     [ ア ],
    PRIMARY KEY (product_id)
);
CREATE TABLE order_item (
    order_no  INTEGER  NOT NULL,
    line_no    INTEGER  NOT NULL,
    product_id    CHAR(4)  NOT NULL,
    quantity      INTEGER  NOT NULL CHECK (quantity > 0),
    [ イ ],
    [ ウ ],
    FOREIGN KEY (product_id) REFERENCES product (product_id)
);
```
- **エ**: 経理課に、注文明細表の参照だけを許可する
- **オ**: 仕入課に、商品表の**単価の更新だけ**を許可する（ほかの列は更新させない）

<details><summary>ヒント</summary>

- ア: NOT NULL のあとに、範囲を制限する制約（定義域制約）
- イ: 2列の主キーは、1つのかっこの中に2列を並べる
- ウ: 外部キーの末尾に、親が消えたときの動き
- オ: `GRANT 権限 (列) ON 表 TO ユーザ`
</details>

## B 検索
`06_s2_data.sql` を入れてから。

- **カ**: 注文ごとの合計金額（期待: 1→2000、2→3000、3→8000）
- **キ**: 顧客ごとの合計金額が、**顧客ごとの合計の平均**を上回る顧客（期待: sasaki 8000）
- **ク**: 一度も注文していない顧客（期待: ito）。EXISTS系で書け
- **ケ**: 月ごとの注文件数（期待: 2026-10→1、2026-11→2）

<details><summary>ヒント</summary>

- カ: 注文明細と商品を結合 → 単価×数量の合計 → 注文番号ごと
- キ: 顧客・注文・明細・商品を結合して顧客ごとに合計 → HAVING で、副問合せの結果（顧客ごとの合計の平均）と比べる。副問合せは、集計の集計になる
- ク: `NOT EXISTS (SELECT 1 FROM orders WHERE orders.customer_id = customer.customer_id)`
- ケ: 日付の先頭7文字（`SUBSTR(order_date, 1, 7)`）で GROUP BY
</details>

## C 更新
- **コ**: 値上げを、**1回のUPDATE**で行う。単価が1000円未満なら+10円、1000円以上なら+100円
- **サ**: 注文番号1の注文を削除する。明細はどうなるか（確認の検索も書け）

<details><summary>ヒント</summary>

- コ: SET の右辺に CASE 式
- サ: 注文だけを DELETE して、明細の件数を数える
</details>

## D 設計の問い
1. 注文明細に「単価」の列を持たせるべきか。持たせるなら、何のためか
2. 注文明細の主キーが2列なのはなぜか

<details><summary>考え方</summary>

1. 商品の単価は商品表に1か所だけ持つのが正規化の基本。ただし、**値上げの前の注文の金額を、後から正しく出す**ためには、注文時点の単価を明細に持たせる設計もある。どちらを採るかは、本文の要件（過去の金額を再現するか）で決まる
2. 1つの注文に複数の行が入るので、注文番号だけでは行を特定できない。注文番号＋行番号で1行が決まる（複合主キー）
</details>

| 大会議室 | `large_room` |
| 小会議室 | `small_room` |

## 場面
会議室を、日付と時間帯（A=午前、B=午後）で予約する。**同じ会議室を、同じ日の同じ時間帯に、二重に予約できない**。

## 条件表
| 表 | 列 | 条件 |
| --- | --- | --- |
| 会議室 | 室ID | 3桁の固定長文字。主キー |
| 会議室 | 室名 | 20桁以内の可変長文字。空にできない |
| 会議室 | 定員 | 整数。空にできない。0より大きい値に限る |
| 利用者 | 利用者ID | 3桁の固定長文字。主キー |
| 利用者 | 氏名 | 20桁以内の可変長文字。空にできない |
| 予約 | 室ID、予約日、時間帯 | **3列の組**で主キー（これで二重予約を防ぐ）。室IDは会議室表を参照 |
| 予約 | 予約日 | 日付 |
| 予約 | 時間帯 | 1桁の固定長文字。**「A」か「B」のどちらか**に限る |
| 予約 | 利用者ID | 3桁の固定長文字。空にできない。利用者表を参照 |

## A 定義・権限
```sql
CREATE TABLE reservation (
    room_id      CHAR(3)  NOT NULL,
    reserve_date    DATE     NOT NULL,
    time_slot    CHAR(1)  [ ア ],
    user_id  CHAR(3)  NOT NULL,
    [ イ ],
    [ ウ ],
    FOREIGN KEY (user_id) REFERENCES room_user (user_id)
);
```
- **エ**: 予約表の参照を全社員に、追加と削除を総務課だけに許可する（GRANT文を2つ）

<details><summary>ヒント</summary>

- ア: 「AかBのどちらか」→ 定義域制約（`IN (...)`）
- イ: 「3列の組で主キー」。ウ: 室IDの「〜を参照」
- エ: 権限は複数並べられる（`GRANT INSERT, DELETE ON ...`）
</details>

## B 検索
`06_s3_data.sql` を入れてから。

- **オ**: 会議室ごとの予約件数。予約がない会議室も 0 で出す（期待: large_room3・small_room2・interview_room0）
- **カ**: **同じ日に2件以上**予約した利用者（期待: sato 2026-11-16）
- **キ**: 2026-11-16 の**午前（A）に空いている**会議室（期待: interview_room）
- **ク**: 定員が**最大**の会議室の名前（期待: large_room）

<details><summary>ヒント</summary>

- オ: 会議室を左にして左外部結合 → `COUNT(reservation.room_id)`（`COUNT(*)` だと0件が1になる）
- カ: 利用者×日付ごとに数える → HAVING で2以上
- キ: 「予約が存在しない会議室」→ `NOT EXISTS`。副問合せに、室ID・日付・時間帯の3つの条件
- ク: `WHERE capacity = (SELECT MAX(capacity) FROM room)`
</details>

## C 更新・エラーの確認
- **ケ**: 2026-11-17 午前の小会議室の予約を取り消せ（主キー3列をすべて指定する）
- 次のSQLを実行すると、どうなるか。理由とともに言え
  ```sql
  INSERT INTO 予約 VALUES ('R01','2026-11-16','A','U03');
  DELETE FROM 利用者 WHERE 利用者ID = 'U01';
  ```

<details><summary>答え合わせの観点</summary>

- 1つ目: 主キー違反（二重予約）で失敗する
- 2つ目: 予約表が参照しているので、外部キー違反で失敗する（`ON DELETE` を指定していない場合）
</details>

## D 設計の問い
1. 利用者と会議室の関係は、何対何か。予約表は何にあたるか
2. 時間帯を主キーに入れずに、予約表の主キーを（室ID、予約日）だけにすると、何が困るか

<details><summary>考え方</summary>

1. 多対多。予約表は**連関実体**で、2つの表の主キーを組み合わせた複合主キーを持つ
2. 同じ日の午前と午後を別々に予約できない（1日1件しか入らない）
</details>

## 場面
会員がポイントをため、使う。**ポイントがマイナスになってはいけない**。ポイントの更新と履歴の追加は、同時に成功するか、同時に失敗しなければならない。

## 条件表
| 表 | 列 | 条件 |
| --- | --- | --- |

| 会員 | 氏名 | 20桁以内の可変長文字。空にできない |

| ポイント履歴 | 増減 | 整数。空にできない（プラスは付与、マイナスは使用） |
| ポイント履歴 | 日付 | 日付。空にできない |

## A 定義・権限
```sql
CREATE TABLE member (
    member_id  CHAR(4)     NOT NULL,
    name    VARCHAR(20) NOT NULL,
    points  INTEGER   [ ア ],
    PRIMARY KEY (member_id)
);
CREATE TABLE point_history (
    history_id  INTEGER  NOT NULL,
    member_id  CHAR(4)  NOT NULL,
    delta    INTEGER  NOT NULL,
    event_date    DATE     NOT NULL,
    PRIMARY KEY (history_id),
    [ イ ]
);
```
- **ウ**: 経理課に、ポイント履歴表の参照だけを許可する
- **エ**: 会員システムに、会員表の参照と、**ポイント列だけの更新**を許可する
- **オ**: 会員システムに与えていた、ポイント履歴表の削除権限を取り消す

<details><summary>ヒント</summary>

- ア: 型のあと、**DEFAULT → NOT NULL → CHECK** の順
- オ: 取り消しは `REVOKE 権限 ON 表 FROM ユーザ`（TO ではない）
</details>

## B 検索
`06_s4_data.sql` を入れてから。

- **カ**: ランク表示。300以上は「ゴールド」、100以上は「シルバー」、それ以外は「ブロンズ」
- **キ**: 履歴が1件もない会員（期待: takahashi）
- **ク**: 会員表のポイントが、**履歴の合計と合わない**会員（期待: suzuki 160 と 150）
- **ケ**: 月ごとの付与ポイントの合計（増減がプラスのものだけ。期待: 2026-09→500、2026-10→150）

<details><summary>ヒント</summary>

- カ: CASE WHEN … THEN … ELSE … END
- キ: 外部結合 ＋ 右側の主キーが空
- ク: 会員ごとに履歴の合計を副問合せで出して比べる。履歴がない会員は SUM が NULL になるので、`COALESCE(…, 0)` で0にそろえる
- ケ: WHERE で増減>0 → 月ごとに SUM
</details>

## D 設計の問い
1. 会員表の「ポイント」は、履歴の合計から求められる。それでも列として持たせる利点と、危険は何か（B のクで見つけたもの）
2. 同じ会員に2人が同時にポイントを使おうとしたとき、起きる問題と、防ぐしくみは何か

<details><summary>考え方</summary>

1. 利点: 残高を、履歴を足し合わせずに読める。危険: 履歴と食い違う（鈴木のように）。処理を必ず同じトランザクションで行うことで防ぐ
2. 2人とも同じ残高を読んで更新すると、片方の更新が消える（更新の取りこぼし）。**専有ロック**で、更新する間はほかの更新を待たせる
</details>
