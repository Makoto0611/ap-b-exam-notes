## 1. アジャイル開発（スクラム）

出題: 令7秋、令6秋、令3秋

### 役割
| 役割 | 内容 |
|---|---|
| プロダクトオーナ | 製品の価値に責任を持つ。要求の優先順位を決め、プロダクトバックログを管理する |
| スクラムマスタ | スクラムの進め方を支援し、障害を取り除く（管理者ではない） |
| 開発チーム | 自己管理で、成果物（インクリメント）を作る |

### イベントと成果物
| 用語 | 内容 |
|---|---|
| スプリント | 1〜4週間程度の固定期間の反復 |
| プロダクトバックログ | 実現したい項目の、優先順位つき一覧 |
| スプリントバックログ | そのスプリントで行う項目と作業 |
| スプリントプランニング | 何を行うか、どう行うかを決める |
| デイリースクラム | 毎日の短い同期（進捗、課題） |
| スプリントレビュー | 成果物を関係者に見せ、フィードバックを得る |
| レトロスペクティブ | プロセスの振り返りと改善 |

### 進捗の見方
- ベロシティ: 1スプリントで完了できる量。次の計画の目安にする
- バーンダウンチャート: 残作業量の推移。計画線との差で、遅れを見る
- チケット（かんばん）: タスクを1枚ずつ可視化する。途中でタスクが増えたら、チケットを発行して、残作業に反映する（管理から漏れないようにする）

### 出題の観点（講評から）
- 日々のタスクの決定は、残チケット数の可視化だけが目的ではなく、「優先度の高いものを期限内に終える」というプロジェクトの目的のために行う（令7秋 2(2)）
- スプリント途中で、関係者の認識が合わないときは、プロダクトオーナなど役割を持つ人と、要求を調整するプロセスを作る（令3秋 3(1)）
- アジャイルの採用は、技術だけでなく、市場の変化に素早く対応して競争力を保つという経営面の背景がある（令3秋 2(1)、令6秋 2(2)）
- 混在開発（ウォーターフォールとアジャイル）は、それぞれの適用範囲と、境界での調整を決めておく（令7秋）

## 2. CCPM（クリティカルチェーン・プロジェクトマネジメント）

出題: 令7春

- 考え方: 各作業の見積りに含まれる安全余裕を削り、プロジェクト全体で共有するバッファに集める
- 背景の現象
  - パーキンソンの法則: 仕事は、与えられた時間いっぱいまで膨らむ
  - 学生症候群: 期限の直前まで着手しない
- 主な仕組み
  - クリティカルチェーン: 作業の依存関係に加え、資源（人）の競合も考慮した、最長の経路
  - プロジェクトバッファ: クリティカルチェーンの最後に置く
  - 合流バッファ: クリティカルチェーンに合流する経路の最後に置く
  - マルチタスクの抑制: 1人が複数作業を同時に抱えない
- 効果: 納期の遅延を最小限に抑える。バッファの消費を見て、進捗を可視化する。資源が足りない作業に、他の要員が応援に入る協力体制を作れる
- 出題の観点: 遅れそうなときに「スケジュールを延期」ではなく、バッファの消費を見て、要員を移して対応する（令7春 3(2)）

## 3. 加重総和法

出題: 令7春（調達や選定の評価方法）

- 評価項目ごとの点数に、重要度の重み（重み付け）を掛けて、合計する評価方法
- 使う場面: ベンダーの選定（提案の評価）、ツールの選定
- 手順
  1. 評価項目を決める
  2. 項目ごとに重みを決める（合計100%など）
  3. 候補ごとに、項目別の点数を付ける
  4. 点数×重みを足して、総合点で比較する
- 令5秋のベンダーの比較（出題）も、この考え方の類題

## 4. フィット＆ギャップ分析

出題: 平31春

- 目的: パッケージソフトウェアやSaaSの標準機能と、業務要件を比べ、合っている点（フィット）と、合っていない点（ギャップ）を洗い出す
- 作業内容
  1. 業務要件の一覧を作る
  2. 標準機能との適合を確認する
  3. ギャップごとに、対処方法を決める（業務を変える／アドオン・カスタマイズする／運用で補う）
  4. 工数・コスト・スケジュールへの影響を評価する
- 重要: パッケージやSaaSの導入では、必須の作業項目

## 5. 移行方式

出題: 令5春

| 方式 | 内容 | 特徴 |
|---|---|---|
| 一括移行 | 全拠点・全機能を、一度に新システムへ切り替える | 移行期間が短く、二重運用がない。失敗時の影響が大きい。業務停止の期間を、営業日以外に絞れる |
| 段階移行 | 拠点や機能ごとに、順に切り替える | リスクを分散できる。移行期間が長く、新旧の併存が必要 |
| 並行稼働 | 新旧を同時に動かして、結果を比べる | 安全だが、二重の運用コストがかかる |

- 設問では、本文の制約（拠点の営業日に業務を止められない、など）を読んで、方式の特徴と結びつける。

## 6. 決定の手続・体制

出題: 令5春

- ステアリングコミッティ（運営委員会）: プロジェクトの重要な意思決定（予算、スコープ、スケジュールの大きな変更）を承認する会議体
- PMは、重要な決定を、ステアリングコミッティの承認を得て進める
- 決定の前提として、他社の事例だけでなく、自社の現状（技術力、人員、体制）を把握する（令5秋 1(2)）

## 7. 契約・調達の補足

### 請負契約での発注者の権利（令4春で「低い」）
- 請負契約では、契約条件に含まれていなければ、発注者は完成前に品質を確認する権利がない
- 対策: 受注者と合意のうえで、契約に条項を加える
  - 中間成果物の確認、レビュー、進捗報告の機会を決める
  - 検収の基準を決めておく

### 多段階契約（令3春）
- 工程ごとに契約を分ける方式。要件定義・基本設計は準委任、以降は請負、とする例が多い
- 上流で内容を固めてから、下流の金額を確定できる
- 見積りは、工程ごとに行う（初回の見積り、2回目の見積りで精度を高める）

### コストベースラインとマネジメント予備（令3春で「やや低い」）
- コストベースライン: 承認された、時間軸に沿った予算。社内承認と、顧客との合意を経たもの
- マネジメント予備: 未知のリスクに備える予備。コストベースラインの外にある
- 追加予算を、ベースラインの外で確保しているなら、それはマネジメント予備にあたる

### 類推見積り（令3春で「低い」）
- 過去の類似プロジェクトの実績から推定する
- 精度を上げる条件: 「類似」していて、かつ「複数」のプロジェクトと比較する（1件では偏る）

### ファンクションポイント法（令3春で「低い」）
- 利用者の視点で見える機能（入力、出力、照会、データ）を数え、複雑さで点数を付けて、規模を測る
- 開発言語に依存しない。仕様段階でも見積もれる

## 8. 品質・テスト（令2秋、令6春）

### 現行システムとの比較テスト
- 目的: 新システムの出力（金額など）が正しいことを、現行システムの結果と比較して検証する
- 使う場面: システム更改で、計算結果の同一性が重要なとき（請求額、残高など）
- 並行稼働テストで、同じ入力を両方に与えて、出力を比べる

### 品質とQCDS（令6春）
- 品質は、スコープ・スケジュール・コストの3つの制約から影響を受ける
- 途中で変更が起きたら、3つを合わせて調整する（スコープを減らす／期間を延ばす／コストを増やす）。品質は、後回しにしない
- スコープの追加は、ルール（承認手続、影響分析）を決めて管理する。個々の要求が小さくても、積み重なるとスコープクリープになる

### 要求の追加・変更への対応（令4春）
- プロトタイピングは、利用部門の意見を取り込みやすい一方、要求の追加・変更が膨らむ
- 対策: 要求を出せる時期と、対応する件数の上限を、利用部門と合意する

## 9. 複数拠点の開発（令元秋）

- 拠点間のコミュニケーションエラーが起きやすい
- 対策の例: 共有ファイルサーバや、課題管理の共通ツールで情報を一元化する。ルール（連絡の経路、様式）を決める
- 注意: プロトタイピングは、画面の確認には有効だが、拠点間の認識齟齬を直す手段ではない（設問が問う種類を確認する）
