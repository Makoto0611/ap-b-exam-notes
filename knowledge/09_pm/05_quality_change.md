## 1. レビューの形態

| 形態 | 進め方 | 特徴 |
|---|---|---|
| インスペクション | 主催者（モデレーター）が進行し、役割を決めて、正式な記録を残す | 最も厳格。欠陥の検出が目的 |
| ウォークスルー | 作成者が説明しながら、関係者が確認する | 理解の共有 |
| パスアラウンド | 設計書を複数のレビュアに配布・回覧する | 会議なしで確認できる |
| ラウンドロビン | 参加者が、持ち回りで司会・説明する | 全員が参加 |

- インスペクションのモデレーター: 全体のコーディネート、意思決定のルールに従って評価を導く。選ぶときは、設計の当事者を避け、公平な第三者（別グループのリーダーなど）にする。
- 出題: 令4秋 問8 設問1・2（レビュー技法の種類、モデレーターに選ぶ人物。本文の字句で書く）。

## 2. 欠陥の用語

| 用語 | 意味 |
|---|---|
| 欠陥 | 要求と異なる不具合 |
| 二次欠陥 | 欠陥を修正したことで、新たに生じる欠陥 |
| 摘出 | レビューやテストで見つける |
| 検出 | 欠陥の存在を見つけること |

- 修正後は、新たな欠陥（二次欠陥）が生じないことを確認する。
- 出題: 令4秋 問8 設問1(3)（「二次欠陥」を本文の字句で）。

## 3. 品質の定量管理

### 基本測定量と指標
- レビュー指摘密度 ＝ 指摘件数 ÷ 規模（ページ、行など）
- レビュー工数密度 ＝ レビュー工数 ÷ 規模
- 欠陥検出密度、バグ密度 ＝ 欠陥数 ÷ 規模

### 管理図
- 管理上限（UCL）と管理下限（LCL）を設け、範囲外を異常として確認する
- 指標が「高いほど良い」「低いほど良い」で、上限・下限の意味が変わる
- IPA講評（令4秋 問8 設問3(1)、低い）: UCL・LCLを設ける理由は、値が大き過ぎるときも小さ過ぎるときも、問題があるおそれがあるから。レビュー指摘密度が低いときは、品質が高い場合と、レビューのプロセスに問題があり欠陥を検出できていない場合がある。品質が高いと判断できる理由は、問題文や表の状況から読み取る。
- LCLが不要な場合の考え方（令4秋 問8 設問3(1)。以下は講評ではなく、解き直しでの整理）
  - その指標は、下限を割っても問題にならない場合がある
  - 例: 誤字・脱字・表記ルール違反のような単純な欠陥は、ツールで抽出できる、または設計途中のレビューで排除済みなので、指摘が少ないことは異常を示さない

### ゾーン分析
- 2つの指標を縦横の軸に取り、領域（良好、レビュー不足、品質問題など）に分けて、対応を決める
- 点が、UCL・LCLのどこに位置するかを読み取り、領域の定義と照らす

## 4. 品質管理の7つ道具

| 道具 | 用途 |
|---|---|
| パレート図 | 原因を件数順に並べ、重点課題を見つける |
| 特性要因図 | 原因の候補を整理する |
| ヒストグラム | データの分布を見る |
| 散布図 | 2つの値の相関を見る |
| 管理図 | 値のばらつきを時系列で監視する |
| チェックシート | 点検項目を記録する |
| 層別 | データをグループ分けして見る |

### 信頼度成長曲線（バグ曲線）
- テストの経過に伴う累積バグ数のグラフ。S字になり、収束（傾きが小さくなる）が出荷の判断材料になる
- 収束しないなら、品質に問題があるか、テストが不十分

## 5. 集合ミーティングの運営

- 集合ミーティングでは、欠陥の検出（指摘）に集中する。修正方法の議論は、別のタイミングで行う。
- 議論が長引き、予定時間を超えたら、指摘だけを行うルールに戻す。
- 出題: 令4秋 問8 設問3(3)（グループEへの改善指針。解答例は「集合ミーティングでは欠陥の指摘だけ行う」）。
- 解き方: 表のルール（検出と対策の議論は別のタイミング）を、各グループの状況に1つずつ当てはめる。

## 6. 変更管理

### 流れ
1. 変更要求
2. 影響分析（スコープ・スケジュール・コスト・品質・リスク）
3. 審査・承認（変更管理委員会：CCB）
4. 実施
5. 検証・記録

- 計画の段階で、変更の「成果」（何が良くなるか）を測定可能な形で決めておく。導入や構築は手段であり、成果ではない。
- 出題: 令4秋 問10 設問1（成果を、本文の字句で。解答例は「売掛金の回収率を高める」）。

### サービス変更の工数
- 作業工数の算出では、本文の条件（注記）で「含める作業」と「含めない作業」を確認する。
- 運用担当者の確認作業は工数に含め、システム処理の時間は含めない、といった指定がある。
- 出題: 令4秋 問10 設問3(1)（システム処理を足してしまう誤りが多かった）。

## 7. 構成管理

| 用語 | 意味 |
|---|---|
| 構成品目 | 管理の対象（成果物、ソース、設計書など） |
| ベースライン | 承認済みで、変更に手続きが必要になる基準点 |
| 版数管理 | 変更履歴を管理する |
| 構成管理と変更管理の違い | 構成管理＝「何がどの版か」を管理／変更管理＝「変更してよいか」を決める |

- 実務の対応: Gitのブランチ・タグ＝構成管理、プルリクエストのレビュー・承認＝変更管理。
