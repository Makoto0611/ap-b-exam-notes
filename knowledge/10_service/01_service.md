# 問10 サービスマネジメントの知識メモ

過去問の本文は載せない。用語・計算の型・出題の観点だけを書く。
出題テーマは `../../past-topics/10_service.md`。ITILやISO/IEC 20000の考え方に基づく一般知識が中心。「低い」「高い」などの評価の記述は、IPA講評の原文（PDF）と照合済み（2026-11-15）。

---

## 1. サービスマネジメントの全体像

| 用語 | 意味 |
|---|---|
| サービス | 利用者が価値を得る手段。利用者が、費用やリスクを負わずに、成果を得られる |
| サービスレベルアグリーメント（SLA） | サービス提供者と利用者の、合意した、サービスの水準 |
| サービスレベル管理（SLM） | SLAの内容を決め、守れているか監視し、見直す |
| 継続的改善 | 計画 → 実行 → 評価 → 改善（PDCA）の繰返し |

### 成果と手段の区別（令4秋）
- 成果: サービスを使って、利用者（顧客）が得る良い変化（例: 売掛金の回収率が上がる）
- 手段: 成果を得るための、方法や仕組み（例: システムを構築する、導入する）
- 設問が「成果」を聞いているのに、手段（導入・構築）を答えるのは、よくある誤り。本文の、サービスの目的に書かれた、顧客側の変化を探す。

## 2. サービスデスクとインシデント管理（令4春、令7秋、令6春）

### サービスデスク
- 利用者の問合せ・障害の連絡を受ける、単一の窓口（SPOC）。
- 窓口を一本化する理由（令7秋で「低い」）
  - 利用者が、どこに連絡すればよいか迷わない
  - 記録が一か所に集まり、重複した対応や、抜け漏れを防げる
  - 問合せの傾向を分析して、改善に使える
- 開発課などから、運用（サービスデスク）への引継ぎ（令6春で「低い」）: 新サービスの開始前に、手順書、よくある問合せの回答、既知の問題、連絡先を、サービスデスクに渡し、受入れの準備を整える。

### インシデント管理
- インシデント: サービスの中断や品質の低下（障害や、その一歩手前の事象）
- 目的: **できるだけ早く、サービスを復旧する**。原因の究明は、後回しでもよい。
- 流れ: 検知・記録 → 分類・優先度付け → 初期診断 → 調査・対応 → 解決・復旧 → クローズ
- 優先度 ＝ 影響度（どれだけの利用者・業務に影響するか）× 緊急度（どれだけ急ぐか）
- 回避策（ワークアラウンド）: 根本原因は直さずに、サービスを復旧・継続させる一時的な手段。インシデントの復旧には、回避策でよい（令4春）。

### エスカレーション（令4春で「低い」）
| 種類 | 内容 |
|---|---|
| 機能的エスカレーション | 自分では解決できないので、**より専門的な技術を持つ人・チーム**に引き継ぐ |
| 階層的エスカレーション | 対応が遅れる、重大なので、**上位の管理者**に報告・判断を求める |

- 判断のしかた: 「技術力が足りない → 機能的」「権限・判断が必要（重大・期限）→ 階層的」。

## 3. 問題管理（令4春）

| 用語 | 内容 |
|---|---|
| 問題 | 1つ以上のインシデントの、原因（まだ根本原因が分かっていない状態） |
| 根本原因分析 | 問題の原因を調べる |
| 既知の誤り | 原因が分かっており、回避策がある（まだ恒久対策はされていない）問題 |
| 既知の誤りデータベース（KEDB） | 既知の誤りと、その回避策を記録したもの。インシデント対応で参照する |
| 恒久対策 | 根本原因を取り除く（変更管理を通して、実施する） |

- インシデント管理と問題管理の違い
  - インシデント: 今のサービスを、早く復旧する
  - 問題: 同じインシデントが、繰り返されないように、原因を取り除く
- 令4春 3(1)（低い。IPA講評の要約）: 問題の抽出条件では、「回避策があるか」ではなく、「根本原因や解決策の特定が必要か」を見る。回避策でインシデントが復旧できても、原因が残っていれば、問題として扱う。
- 令4春 2(2)（低い。IPA講評の要約）: 機能的エスカレーションで待たされる時間を減らすには、既知の誤りを調べ、回避策があれば適用する。

## 4. 変更管理・展開管理（令3秋、令4秋、令6春）

### 変更管理
- 目的: 変更による、サービスへの悪い影響を、最小限にする。
- 変更要求（RFC）: 変更したい内容の申請書。
- 流れ: RFC → 評価（影響・リスク・費用）→ 承認（変更諮問委員会 CAB）→ 計画 → 実施 → レビュー
- 変更の種類

  | 種類 | 内容 |
  |---|---|
  | 標準変更 | 手順が決まっていて、リスクが低い、定型の変更。事前に承認されている |
  | 通常変更 | RFCを出して、評価・承認を受ける |
  | 緊急変更 | 重大なインシデントなど、急ぐ変更。簡略化した手順で承認し、事後に検証する |

- 優先度が「低」のRFCの承認権限（令3秋で「やや低い」）: 影響が小さい変更は、CABを毎回開かず、変更管理の責任者や担当者に、権限を委譲して、承認を早める。
- 通常変更の移管（令6秋）: 新しいサービスの運用開始後は、通常変更として、運用側の変更管理プロセスに移す。

### 展開管理（リリース・展開管理）
| 用語 | 内容 |
|---|---|
| 展開計画 | いつ、誰が、どの順で、変更を本番に展開するかの計画 |
| 切戻し計画 | 展開がうまくいかなかったとき、元の状態に戻す手順と、判断基準 |
| 受入れテスト | 利用部門が、要件を満たしているかを確認する |
| 展開後レビュー | 結果を確認し、改善する |

- 令3秋 2(3)（低い）: 展開計画と切戻し計画。計画には、実施時期と手順に加え、失敗の判定基準と、戻す手順を含める。
- 令6春 3（やや低い）: 展開管理とOSパッチ。IPA講評は、「展開管理の視点から」OSパッチの適用に必要な対策を本文から読み取るべきところを、統合管理ツールの機能だけに触れた誤答が多かった、とする。展開管理の意味（展開計画、切戻し、受入れなど）を理解する。
  - 一般知識: 多数の端末に展開するなら、一斉ではなく段階的に展開し、問題が出たら止められるようにする。

## 5. サービスレベル（SLA）と可用性（令7春、令5春、令3春、平31春）

### SLAの構成要素
| 項目 | 内容 |
|---|---|
| サービス提供時間 | サービスを提供すると約束している時間帯（例: 平日9〜21時） |
| 計画停止 | あらかじめ決まっている、保守のための停止。サービス提供時間に含めないか、除外して計算する |
| 稼働率（可用性） | 約束した提供時間のうち、実際に使えた割合 |
| 目標値 | 守ると合意した数値（例: 稼働率99.9%以上） |
| 応答時間、復旧時間 | 問合せへの回答、障害復旧にかかる時間の目標 |

### 稼働率の計算
- 稼働率 ＝ （サービス提供時間 − 停止時間）÷ サービス提供時間
- 停止可能な時間 ＝ サービス提供時間 × （1 − 目標稼働率）
- 計画停止は、本文の定義で、分母から除くか、停止時間に含めないかを確認する。本文の条件で、含める時間と除く時間を決める（令7秋の設問）。
- MTBFとMTTRを使う場合: 稼働率 ＝ MTBF ÷ （MTBF ＋ MTTR）

### SLAの注意（令7春、令5春、平31春、令3春）
- SLAは、サービス提供者と利用者の間で、合意した水準。インシデントが起きたことを、理由に、一方的に変えない。
- 令7春 1(1)（やや低い）: SLAを変更せずに、業務に支障を出さない施策。SLAの水準を保ったまま、サービスの余力（容量）を増やす、運用で対応するなど、合意を変えずに実現できる施策を考える。
- 令5春 2(3)（やや低い）: 勤務体制の変更後に調整すべきこと。サービスを提供する人員の体制が変わると、サービス提供時間やサービスデスクの対応時間が、影響を受ける。IPA講評（PDFで確認）: これまでは計画停止が営業時間外だったので、サービス時間のSLAを合意する必要がなかったが、勤務体制の変更後は、計画停止時間を考慮した勤務形態にする必要がある。**「委託先と計画停止時間の変更を協議する」は誤答**として挙がっている。本文の表（サービスカタログ、合意したサービスレベル）を具体的にイメージして答える。
- 平31春 4(1)（低い）: 委託先の保守時間も、計画停止時間に含まれる。保守のために、サービスを止める時間が、計画停止の対象。
- 平31春 5（低い）: リソースの増強を要求する根拠として、利用状況の実績（キャパシティの傾向）を、データで示す。

### 内部供給者との合意
| 契約 | 当事者 |
|---|---|
| SLA | サービス提供者と、顧客（利用者） |
| 運用レベルアグリーメント（OLA） | サービス提供者と、組織内の別部門（内部供給者） |
| 契約（UC） | サービス提供者と、外部の供給者（委託先） |

- 令5秋 2(2)（やや低い）: 内部の供給者との合意。社内の別部門が、サービスの一部を担うなら、その部門とOLAを結び、SLAの達成を支える。

### 可用性管理・キャパシティ管理（令7春、令5春）
- 可用性管理: 合意した可用性を満たすように、設計・運用を管理する。冗長化、遠隔地バックアップ（令5春）など。
- キャパシティ管理: 現在と将来の、サービスの需要を満たす、資源（CPU、ストレージ、回線）を確保する。
- クラウドの柔軟性: 需要に合わせて、資源を増減できる（令7春 2(2)）。需要の変動が大きいサービスに向く。
- サービス継続: 災害などで、サービスが止まったときの、復旧の目標（目標復旧時間 RTO、目標復旧時点 RPO）を決めて、備える。

## 6. KPIと改善（令元秋、令7秋、令6秋）

| 用語 | 内容 |
|---|---|
| CSF（重要成功要因） | 目的を達成するために、成功させるべきこと |
| KPI（重要業績評価指標） | CSFの達成度を測る、具体的な指標（数値） |
| 目標値 | KPIで、達成したい水準 |
| 実績値 | 実際に測定した値 |

- 令元秋 1(3)(4)（低い）: KPIと目標値、実績値の評価。指標（何を測るか）、目標値（いつまでに、どれだけ）、実績値（実際）を区別し、実績が目標に届いたか、届かなかったら何を見直すかを、本文の数値から読む。
- 例: 問合せの自己解決率（令7秋 4(2)、平均的）。IPA講評: 改善手順はおおむね理解されていたが、問題文に書かれていない項目を答える誤答が散見された。サービスデスクの具体的なオペレーションを考えるときは、内部で管理しているデータベースにどんなデータが入っているかを確認する。
  - 一般知識: FAQの内容の充実、検索のしやすさ、利用者への周知が、自己解決率を上げる施策になる。
- 改善活動の定着（令元秋 設問2、高い）: IPA講評は、運用部門のトップが、マネジメント方針と評価基準を示し、改善に必要な体制を作ることが重要、とする。

## 7. サービスの費用（令2秋）

| 用語 | 内容 |
|---|---|
| 直接費 | 特定のサービス・顧客のために、直接かかった費用（そのサービス専用の機器、担当者の作業費） |
| 間接費 | 複数のサービスで共有して使う費用（共通の設備、管理部門の費用） |
| 配賦（按分） | 間接費を、一定の基準で、各サービスに割り当てる |

- 令2秋 2(2)、3(2)（やや低い）: 直接費と間接費の定義、利用者数や利用時間による按分。
- 按分の型: 配賦額 ＝ 間接費の合計 × （そのサービスの利用量 ÷ 全体の利用量）
  - 基準は、本文が指定する（利用者数、利用時間、処理件数など）。公平に、利用量に比例させる。

## 8. 工数・時間の計算（令4秋、令6秋）

- 変更や作業の工数は、本文の条件で、**含める作業**と**含めない作業**を決める（令4秋 3(1)で、システム処理の時間を足してしまう誤りが多かった）。
- 型: 工数 ＝ 件数 × 1件あたりの作業時間。人が行う作業と、システムが自動で行う処理を、区別する。
- 単位（分、時間、人日、人月）を設問に合わせる。1人日 ＝ 8時間などの換算は、本文で確認する。
- 令6秋 4（必要工数。IPA講評の要約）: 平均のサービス要求件数と平均対応時間から、必要な工数を出す。需要の増加や、要求が集中する時間帯を考慮して、余裕を持たせる。

---

## 9. 解き方メモ

1. 用語の穴埋めは、サービスマネジメントの、プロセス名（インシデント／問題／変更／展開／SLM）で、どれの話かを、まず決める
2. 「復旧」はインシデント、「原因の除去」は問題、「変更の承認」は変更管理、と目的で分ける
3. SLAに関する設問は、「合意した水準を変えない」「本文の表（サービス提供時間、計画停止）を、イメージして読む」
4. 計算は、本文の条件で、含める時間と除く時間を表に書いてから、計算する
5. 「成果」は顧客の変化、「手段」は導入・構築、と区別する

## 10. 確認問題

- 先に自分で選んでから ▶を開く対象はこのファイルの内容だけ

**問1** インシデント管理の目的として適切なものはどれか。
ア 根本原因を取り除く　イ できるだけ早く、サービスを復旧する　ウ 変更を承認する　エ SLAの内容を見直す

<details><summary>答えと解説</summary>
イ。原因の究明は後回しでもよく、回避策（ワークアラウンド）で復旧してよい。アは問題管理、ウは変更管理、エはサービスレベル管理の役割。
</details>

**問2** 自分では解決できないので、より専門的な技術を持つ人・チームに引き継ぐエスカレーションはどれか。
ア 機能的エスカレーション　イ 階層的エスカレーション　ウ 優先度エスカレーション　エ 緊急エスカレーション

<details><summary>答えと解説</summary>
ア。「技術力が足りない」なら機能的。イの階層的は、対応が遅れる、重大であるなど、権限や判断が必要なときに、上位の管理者へ報告する。
</details>

**問3** 原因が分かっており、回避策があるが、恒久対策がまだされていない問題を何というか。
ア インシデント　イ 既知の誤り　ウ 変更要求（RFC）　エ 標準変更

<details><summary>答えと解説</summary>
イ。既知の誤りと回避策を記録したものが、既知の誤りデータベース（KEDB）で、インシデント対応で参照する。恒久対策は、変更管理を通して実施する。
</details>

**問4** サービス提供時間が月200時間で、停止時間が2時間だった。稼働率はいくらか。
ア 98%　イ 99%　ウ 99.5%　エ 99.9%

<details><summary>答えと解説</summary>
イ。稼働率＝（サービス提供時間−停止時間）÷サービス提供時間＝（200−2）÷200＝99%。計画停止は、本文の定義で、分母から除くか、停止時間に含めないかを確認する。
</details>

**問5** サービス提供者と、組織内の別部門（内部供給者）との合意はどれか。
ア SLA　イ OLA　ウ UC　エ KPI

<details><summary>答えと解説</summary>
イ。OLA（運用レベルアグリーメント）は、組織内の別部門との合意で、SLAの達成を支える。アは、サービス提供者と顧客の合意。ウは、外部の供給者（委託先）との契約。
</details>

**問6** 重大なインシデントなど、急ぐ変更を、簡略化した手順で承認し、事後に検証する変更の種類はどれか。
ア 標準変更　イ 通常変更　ウ 緊急変更　エ 展開

<details><summary>答えと解説</summary>
ウ。アの標準変更は、手順が決まっていてリスクが低く、事前に承認されている定型の変更。イの通常変更は、変更要求（RFC）を出して、評価・承認を受ける。
</details>
