## 1. スタースキーマとデータマート（令3春、令6春）

### データウェアハウス（DWH）とデータマート
| 用語 | 内容 |
|---|---|
| データウェアハウス | 業務システムのデータを、分析用に集めて、時系列で蓄積した大規模なDB |
| データマート | 特定の部門や目的向けに、DWHから切り出した、小さい分析用DB |
| ETL | 抽出（Extract）、変換（Transform）、書込み（Load）。業務DBから、DWHへデータを移す処理 |
| OLAP | 多次元の集計・分析（ドリルダウン、スライス） |

### スタースキーマ
- 中心に「ファクト表」、周りに「ディメンション表」を置く、星形の設計。
- ファクト表: 分析したい数値（売上金額、数量）と、ディメンション表を指す外部キーを持つ。
- ディメンション表: 分析の切り口（日付、商品、店舗、顧客）。正規化せず、検索を速くすることが多い。
- 利点: 結合が少なく（ファクト表とディメンションの1段だけ）、集計が速い。分析の切り口を増やしやすい。
- スノーフレークスキーマ: ディメンションを、さらに正規化したもの。結合は増えるが、重複は減る。

### 集計表の読み方（令3春 4で「低い」）
- 軸（行・列）に何を置くかを、設問から決める（例: 月ごと × 店舗ごとの売上）。
- 集計のSQLは、ファクト表とディメンション表を結合し、切り口の列で、GROUP BYする。
  ```
  SELECT d.月, s.店舗名, SUM(f.売上金額)
  FROM 売上ファクト f
    INNER JOIN 日付ディメンション d ON f.日付ID = d.日付ID
    INNER JOIN 店舗ディメンション s ON f.店舗ID = s.店舗ID
  GROUP BY d.月, s.店舗名
  ```
- データマートに入れるデータが足りない（データソースの不足）場合は、元のどのシステムの、どの項目を、追加で取り込む必要があるかを、本文から探す（令3春 1）。

## 2. マルチテナントとスキーマの分離（令6春）

- マルチテナント: 1つのシステムを、複数の会社（テナント）が共同で使う方式。
- データの分け方
  | 方式 | 内容 | 長所 | 短所 |
  |---|---|---|---|
  | 共有スキーマ（同じ表に、テナントIDの列を持つ） | 全テナントのデータが、同じ表に入る | 構成が簡単 | 他社のデータが見える危険、検索条件の漏れ |
  | スキーマ分離（テナントごとにスキーマを分ける） | テナントごとに、別の表の集まりを持つ | テナントごとに権限を分けやすい。他社のデータが混ざらない | スキーマの数が増え、管理が複雑 |
  | データベース分離 | テナントごとに、別のDBを持つ | 分離が最も強い | 費用と管理が大きい |
- 令6春 2（低い）: IPA講評は、マルチテナントで情報漏えいの被害範囲をできるだけ狭めること、がセキュリティ上必要で、スキーマを会社ごとに分ける方式で何が実現できるかを、もう一歩踏み込んで考える、とする。
  - 一般知識: ある会社の利用者が、他の会社のデータを見られない（アクセス制御が簡単）。
- 令6春 4(3)（やや低い）: IPA講評は、単一データベース・個別スキーマ方式で、他社のデータも照会できるようにするには、各表をどのスキーマに配置するかを、各スキーマの役割を理解して決める、とする。
  - 一般知識: スキーマは、表、ビューなどを名前の空間としてまとめ、権限（GRANT）の単位にもできる。

## 3. インデックス設計（令6秋）

- 目的: 検索を速くする。列の値から、行の位置を、素早く探せるようにする。
- 効果が出る列: WHERE、JOINの条件、ORDER BYに、よく使う列。値の種類が多い（選択性が高い）列。
- 効果が薄い列: 値の種類が少ない列（性別など）、更新が非常に多い列。
- 代償: 追加、更新、削除のたびに、インデックスも更新するので、**更新が遅くなる**。記憶領域も使う。
- 複合インデックス: 複数の列の組合せ。条件に使う列の、並び順が重要（先頭の列から使われる）。
- LIKE検索との関係: 前方一致（`LIKE '東京%'`）は、インデックスが使える。中間一致・後方一致（`LIKE '%東京'`）は、使えない。
- 令6秋 設問3(2)（低い）: IPA講評は、不適切な列にインデックスを設定すると性能低下を招くおそれがあるので、データ、実行するSQL文、インデックスの種類の特性を踏まえて、必要十分な列だけに設定する、とする。
- 設問では、「どの検索を速くしたいか」から、どの列にインデックスを付けるかを、本文のSQLの条件から決める。

## 4. LIKE述語（令6秋 h で「低い」）

| パターン | 意味 |
|---|---|
| `%` | 0文字以上の任意の文字列 |
| `_` | 任意の1文字 |

- `LIKE '東京%'` ： 「東京」で始まる（前方一致）
- `LIKE '%東京'` ： 「東京」で終わる（後方一致）
- `LIKE '%東京%'` ： 「東京」を含む（部分一致）
- `LIKE '田_'` ： 「田」＋任意の1文字（2文字）
- 本文の「〜で始まる」「〜を含む」と、パターンを対応づける。
- 令6秋 設問2 h（低い。IPA講評の要約）: LIKE述語のオペランドに、埋込み変数（`:変数`）とエスケープ文字を指定するときは、文字値式を連結（`||`）して書く。例: `LIKE '%' || :キーワード || '%'`。`%` や `_` 自体を検索したいときは、`ESCAPE` で、エスケープ文字を指定する。

## 5. ウィンドウ関数（令5秋 i で「やや低い」）

- IPA講評: 空欄に「WINDOW」と誤って答える受験者が多かった。BNF（構文の定義）を正しく読んで答える。
- 集計関数のように計算するが、行をまとめずに、各行に結果を付ける。
- 書き方
  ```
  関数() OVER (PARTITION BY 区切る列 ORDER BY 並べる列)
  ```
  - PARTITION BY: グループに分ける（GROUP BYと似ているが、行は減らない）
  - ORDER BY: そのグループ内の、並び順
- 代表的な関数
  | 関数 | 内容 |
  |---|---|
  | `RANK()` | 順位（同順位があると、次の順位が飛ぶ） |
  | `DENSE_RANK()` | 順位（同順位があっても、飛ばない） |
  | `ROW_NUMBER()` | 行に、連番を付ける |
  | `SUM(列) OVER (...)` | 累計や、グループごとの合計を、各行に付ける |
  | `LAG(列)` / `LEAD(列)` | 前の行／次の行の値 |
- 例: 部門ごとの、給与の順位
  ```
  SELECT 氏名, 部門, RANK() OVER (PARTITION BY 部門 ORDER BY 給与 DESC) AS 順位 FROM 従業員
  ```
- GROUP BYとの違い: GROUP BYは、グループごとに1行にまとめる。ウィンドウ関数は、元の行を、そのまま残す。

## 6. 副問合せと結合（令7春 d、令5春 2(2)）

- IPA講評（令7春 設問2 d、低い）: 副問合せ同士を結合するときは、関連や多重度まで考える。実施したキャンペーンの中に、売上に結びつかないものがある点を考えて、SQL文を組み立てる。
- 副問合せ（サブクエリ）: SELECTの中に、別のSELECTを入れる。
  - WHERE句の中: `WHERE 列 IN (SELECT ...)`、`WHERE 列 > (SELECT AVG(...) ...)`
  - FROM句の中: 副問合せの結果を、仮の表として、結合する（令7春 2 d「副問合せの結合」）
- 副問合せの結果を、仮の表として使うときは、名前（別名）を付けて、結合の条件を書く。
  ```
  SELECT a.顧客ID, b.合計
  FROM 顧客 a
    LEFT OUTER JOIN (SELECT 顧客ID, SUM(金額) AS 合計 FROM 注文 GROUP BY 顧客ID) b
      ON a.顧客ID = b.顧客ID
  ```
- LEFT OUTER JOINの仕様（令5春 2(2)で「低い」）
  - 左の表の行は、全部残る。右に相手がいない行は、右の列が NULL になる。
  - 「注文がない顧客も含めて」と書いてあれば、LEFT OUTER JOIN。
  - 右の表の列を、WHERE句で絞ると、NULLの行が消えて、INNER JOINと同じ結果になることがある（絞込みは、ON句に書くか、IS NULLを考慮する）。

## 7. 排他制御と連番（令4春）

- 連番（クーポンの番号など）を、同時に複数の処理が発行すると、同じ番号が重複することがある。
- 対策の型
  - UNIQUE制約: 同じ値の挿入を、DBが拒否する（業務要件として、重複を許さない場合に定義する。令4春 1(3)）
  - 排他制御: 番号を採る処理を、ロックして、1つずつ実行する
  - シーケンス（連番の生成機能）、自動採番
- `UPDATE 表 SET 列 = 列 + 1 WHERE 条件` のような、更新の形（SET句に、自分の値を使う）は、現在値を読んで、書き戻す、までを、1つの文で行うので、先に読んでから別に更新するより、競合が起きにくい（令4春 3 f）。

## 8. 埋込み変数（令3秋 f、令元秋 e）

- アプリケーションのプログラムの中に、SQLを書くとき、値を入れる場所を、変数で表す。
  ```
  SELECT 氏名 FROM 従業員 WHERE 部署ID = :部署ID
  INSERT INTO 注文 (注文ID, 顧客ID) VALUES (:注文ID, :顧客ID)
  ```
- `:変数名` の形で書き、実行時に、プログラムの値が入る。
- 設問では、INSERT文の列の並びと、VALUESの並びが、対応しているかを確認する。本文に、どの値を、どの変数で渡すと書いてあるかを、探す。

## 9. スーパータイプ／サブタイプ（令7秋 2(2)で「やや低い」）

- 共通の属性を、スーパータイプ（上位の実体）にまとめ、個別の属性を、サブタイプ（下位の実体）に持たせる。
  - 例: 受講者（スーパータイプ：氏名、連絡先）、社内受講者・社外受講者（サブタイプ：所属部署、会社名）
- 関係スキーマにするとき
  - スーパータイプの表を作る（主キー: 共通のID）
  - サブタイプの表の主キーは、スーパータイプの主キーと同じ値にして、**外部キー**にもする（1対1に対応）
- E-R図の読み方: 「〜の一種」の関係。サブタイプは、スーパータイプの主キーを引き継ぐ。
- 令7秋 4h（やや低い。IPA講評の要約）: DDL（CREATE文、ALTER文）で、削除時のアクション（`ON DELETE ...`）を書く。サブタイプの表は `CREATE TABLE` で作り、既存の表に列や制約を足すときは `ALTER TABLE ... ADD`。

## 10. 解き方メモ（追加）

1. 分析・集計の設問は、「ファクト（数値）」と「ディメンション（切り口）」を、まず分ける
2. 「会社ごとにデータを分ける」「他社から見えない」は、テナントの分離（スキーマ、権限）の話
3. インデックスの設問は、「検索が速くなる」と「更新が遅くなる」の、両面を書く
4. 「〜を含めて」「〜がない場合も」は、LEFT OUTER JOIN。WHERE句の絞込みで、NULLの行が消えないかを確認する
5. 本文の条件（「年月ごと」「最小値」「ログインしている」）は、SQLの、GROUP BY・HAVING・WHEREのどこに入るかを、決めてから、空欄に書く

## 11. 確認問題

- 先に自分で選んでから `<details>` を開く。対象はこのファイルの内容だけ

**問1** スタースキーマで、分析したい数値と、ディメンション表を指す外部キーを持つ表はどれか。
ア ファクト表　イ ディメンション表　ウ データマート　エ ETL

<details><summary>答えと解説</summary>
ア。ファクト表は売上金額・数量などの数値を持つ。ディメンション表は分析の切り口（日付、商品、店舗、顧客）。
</details>

**問2** スタースキーマの利点として適切なものはどれか。
ア 結合が少なく、集計が速い　イ 重複が最も少ない　ウ 更新が最も速い　エ 結合が多い

<details><summary>答えと解説</summary>
ア。結合は、ファクト表とディメンションの1段だけ。ディメンションをさらに正規化したスノーフレークスキーマは、結合は増えるが、重複は減る。
</details>

**問3** マルチテナントで、テナントごとにスキーマを分ける方式の長所はどれか。
ア 構成が最も簡単　イ 他社のデータが混ざらず、テナントごとに権限を分けやすい　ウ 費用と管理が最も小さい　エ 検索条件の漏れが起きやすい

<details><summary>答えと解説</summary>
イ。短所は、スキーマの数が増え、管理が複雑になること。アとエは、同じ表にテナントIDの列を持つ共有スキーマの特徴。データベース分離は、分離が最も強いが、費用と管理が大きい。
</details>

**問4** インデックスの効果が薄い列として、適切なものはどれか。
ア 値の種類が少ない列（性別など）　イ WHEREによく使う列　ウ 値の種類が多い列　エ JOINの条件の列

<details><summary>答えと解説</summary>
ア。値の種類が少ない列や、更新が非常に多い列は、効果が薄い。インデックスの代償は、追加・更新・削除のたびに更新が必要で、更新が遅くなること。
</details>

**問5** LIKE検索で、インデックスが使えるのはどれか。
ア LIKE '東京%'　イ LIKE '%東京'　ウ LIKE '%東京%'　エ どれも使えない

<details><summary>答えと解説</summary>
ア。前方一致は、インデックスが使える。中間一致・後方一致は、使えない。`%` は0文字以上の任意の文字列、`_` は任意の1文字。
</details>

**問6** 「注文がない顧客も含めて」顧客ごとの合計を出すとき、使う結合はどれか。
ア INNER JOIN　イ LEFT OUTER JOIN　ウ CROSS JOIN　エ 使えない

<details><summary>答えと解説</summary>
イ。LEFT OUTER JOINは、左の表の行は全部残り、右に相手がいない行は、右の列が NULL になる。右の表の列をWHERE句で絞ると、NULLの行が消えて、INNER JOINと同じ結果になることがある。絞込みは、ON句に書くか、IS NULLを考慮する。
</details>

**問7** ウィンドウ関数（PARTITION BY）の特徴として適切なものはどれか。
ア グループごとに1行にまとめる　イ 元の行を、そのまま残し、各行に結果を付ける　ウ 行を削除する　エ 表を結合する

<details><summary>答えと解説</summary>
イ。アはGROUP BYの特徴。書き方は、`関数() OVER (PARTITION BY 区切る列 ORDER BY 並べる列)`。PARTITION BYはグループに分け、ORDER BYはそのグループ内の並び順を決める。
</details>
